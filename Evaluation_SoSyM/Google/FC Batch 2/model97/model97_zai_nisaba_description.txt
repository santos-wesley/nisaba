#MP-Declare Model
## Activities
- **Define Project Scope**: The 'Define Project Scope' activity represents the initial phase of a project where the boundaries, objectives, and deliverables of the project are established.
- **Design Database Schema**: The 'Design Database Schema' activity involves creating the structural design of the database, including tables, relationships, and constraints to support the application's data requirements.
- **Develop Frontend Interface**: The 'Develop Frontend Interface' activity encompasses building the user-facing components of the application, ensuring an intuitive and responsive user experience.
- **Implement Backend Logic**: The 'Implement Backend Logic' activity involves coding the server-side functionality of the application, including business rules, data processing, and API development.
- **Integrate Payment Gateway**: The 'Integrate Payment Gateway' activity involves connecting the application to a third-party payment processing service to enable financial transactions.
- **Test System Functionality**: The 'Test System Functionality' activity includes executing various tests on the system to verify that all components work as expected and meet the specified requirements.
- **Deploy Application to Server**: The 'Deploy Application to Server' activity involves transferring the application from a development environment to a live server environment where it becomes accessible to end users.
- **Monitor System Performance**: The 'Monitor System Performance' activity encompasses tracking and analyzing the application's operational metrics, such as response times, resource usage, and uptime, to ensure optimal performance.
- **Gather User Feedback**: The 'Gather User Feedback' activity involves collecting opinions, suggestions, and issue reports from users regarding their experience with the application.
- **Update System Based on Feedback**: The 'Update System Based on Feedback' activity includes making modifications and improvements to the application driven by the feedback received from users.

## Attributes
- **Project Status: Initiated, In Progress, Completed, Delayed**: The attribute 'Project Status: Initiated, In Progress, Completed, Delayed' specifies the possible states of a project, which can be 'Initiated', 'In Progress', 'Completed', or 'Delayed'.
- **Development Time: integer between 10 and 2000**: The attribute 'Development Time: integer between 10 and 2000' represents the amount of time, measured in integer units, spent on development activities, ranging from 10 to 2000.
- **Budget Allocated: float between 1000.0 and 500000.0**: The attribute 'Budget Allocated: float between 1000.0 and 500000.0' represents the financial resources assigned to a development task, expressed as a floating-point value ranging from 1000.0 to 500000.0.
- **Payment Method: Credit Card, PayPal, Stripe**: The attribute 'Payment Method: Credit Card, PayPal, Stripe' specifies the available payment options for processing transactions, which include 'Credit Card', 'PayPal', and 'Stripe'.
- **Number of Users: integer between 0 and 1000000**: The attribute 'Number of Users: integer between 0 and 1000000' represents the count of users interacting with the system, expressed as an integer value ranging from 0 to 1000000.
- **Transaction Volume: float between 0.0 and 10000000.0**: The attribute 'Transaction Volume: float between 0.0 and 10000000.0' represents the total monetary value of transactions processed by the system, expressed as a floating-point value ranging from 0.0 to 10000000.0.
- **Deployment Environment: Development, Staging, Production**: The attribute 'Deployment Environment: Development, Staging, Production' specifies the possible environments where the application can be deployed, which include 'Development', 'Staging', and 'Production'.
- **Number of Bugs: integer between 0 and 1000**: The attribute 'Number of Bugs: integer between 0 and 1000' represents the count of identified defects or issues in the system, expressed as an integer value ranging from 0 to 1000.
- **User Satisfaction: float between 1.0 and 5.0**: The attribute 'User Satisfaction: float between 1.0 and 5.0' represents the level of satisfaction reported by users, expressed as a floating-point value ranging from 1.0 to 5.0.
- **Feedback Type: Bug Report, Feature Request, Improvement Suggestion**: The attribute 'Feedback Type: Bug Report, Feature Request, Improvement Suggestion' specifies the categories of feedback that can be submitted by users, which include 'Bug Report', 'Feature Request', and 'Improvement Suggestion'.

## Constraints
- **Init[Define Project Scope] | |**: The 'Define Project Scope' activity must be the first activity to occur in the process.
- **Precedence[Develop Frontend Interface, Design Database Schema] | | |**: The 'Design Database Schema' activity is permitted to occur only if a 'Develop Frontend Interface' activity has occurred before it within the same process instance.
- **Response[Integrate Payment Gateway, Implement Backend Logic] | | |**: If an 'Integrate Payment Gateway' activity occurs, then an 'Implement Backend Logic' activity must eventually occur after the 'Integrate Payment Gateway' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Integrate Payment Gateway' events can be pending at the same time, and a single 'Implement Backend Logic' can fulfill the obligation for all preceding 'Integrate Payment Gateway' events. If 'Integrate Payment Gateway' does not occur, the constraint imposes no obligation on the occurrence of 'Implement Backend Logic'.
- **Co-Existence[Test System Functionality, Deploy Application to Server] | | |**: If 'Test System Functionality' activity occurs, then 'Deploy Application to Server' must also occur in the same process instance, and vice-versa. The events can occur multiple times and in any order relative to each other. If neither event occurs, the constraint is still considered satisfied.
- **Succession[Deploy Application to Server, Monitor System Performance] | | |**: A 'Deploy Application to Server' activity must be followed by a 'Monitor System Performance' activity at some point later in the same process instance. Conversely, a 'Monitor System Performance' event can occur only if a 'Deploy Application to Server' event has occurred before it within the same process instance. This bidirectional and ordered dependency ensures that 'Deploy Application to Server' imposes obligations for future 'Monitor System Performance', and 'Monitor System Performance' cannot occur without prior 'Deploy Application to Server'. Multiple 'Deploy Application to Server' and 'Monitor System Performance' are allowed, with each 'Deploy Application to Server' eventually leading to a 'Monitor System Performance' and each 'Monitor System Performance' being justified by a preceding 'Deploy Application to Server'.
- **Not Precedence[Define Project Scope, Gather User Feedback] | | |**: A 'Gather User Feedback' activity cannot be preceded by a 'Define Project Scope' activity within the same process instance. This means that if any 'Define Project Scope' event has occurred before a 'Gather User Feedback' event in the process instance, then that 'Gather User Feedback' is disallowed. Multiple 'Gather User Feedback' and 'Define Project Scope' events can occur, but all instances of 'Gather User Feedback' must occur before any instance of 'Define Project Scope'.
- **Not Response[Define Project Scope, Update System Based on Feedback] | | |**: The 'Define Project Scope' activity must not be followed by an 'Update System Based on Feedback' activity at any point later in the same process instance. This means that once a 'Define Project Scope' event occurs, 'Update System Based on Feedback' cannot occur afterward. However, 'Update System Based on Feedback' events occurring before the 'Define Project Scope' are permitted. The constraint ensures that after the occurrence of 'Define Project Scope', the process does not allow any further occurrences of 'Update System Based on Feedback'.
- **Choice[Design Database Schema, Develop Frontend Interface] | | |**: At least one of the activities 'Design Database Schema' or 'Develop Frontend Interface' must occur in the process instance. This means that the process is compliant if 'Design Database Schema' event occurs, 'Develop Frontend Interface' event occurs, or both occur. There is no restriction on the order or the number of times they occur. However, if neither 'Design Database Schema' nor 'Develop Frontend Interface' occurs, the constraint is violated.

## Interleaved Description
The MP-Declare process model for the software development lifecycle process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Define Project Scope,' which represents the initial phase of a project where the boundaries, objectives, and deliverables of the project are established. This activity is linked to the 'Project Status' attribute, which can hold the values 'Initiated,' 'In Progress,' 'Completed,' or 'Delayed,' thereby setting the foundational context for the entire process.

### **Frequency Constraints**

#### **Existence Constraint**
The 'Update System Based on Feedback' activity must occur at least once in the process. This activity involves making modifications and improvements to the application driven by the feedback received from users, linked to the 'Feedback Type' attribute that categorizes feedback as 'Bug Report,' 'Feature Request,' or 'Improvement Suggestion.' This requirement adds depth and reliability to the process by ensuring that user-driven improvements are always incorporated.

#### **Absence Constraint**
The 'Test System Functionality' activity must not occur 5 or more times in the process. This activity includes executing various tests on the system to verify that all components work as expected and meet the specified requirements, linked to the 'Transaction Volume' attribute. This restriction highlights the exclusions and reinforces process integrity by specifying that excessive testing iterations are not permissible, thereby maintaining efficiency.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
The 'Design Database Schema' activity is permitted to occur only if a 'Develop Frontend Interface' activity has occurred before it within the same process instance. The 'Design Database Schema' activity involves creating the structural design of the database, including tables, relationships, and constraints, linked to the 'Development Time' attribute (ranging from 10 to 2000). The 'Develop Frontend Interface' activity encompasses building the user-facing components of the application, linked to the 'Budget Allocated' attribute (ranging from 1000.0 to 500000.0). This sets up an initial context where the frontend interface must be developed before the database schema is designed, guiding the logical sequence within the model.

#### **Response Constraints**
1. If an 'Integrate Payment Gateway' activity occurs, then an 'Implement Backend Logic' activity must eventually occur after it at some point in the same process instance. The 'Integrate Payment Gateway' activity involves connecting the application to a third-party payment processing service, linked to the 'Number of Users' attribute (ranging from 0 to 1,000,000). The 'Implement Backend Logic' activity involves coding the server-side functionality, linked to the 'Payment Method' attribute ('Credit Card,' 'PayPal,' or 'Stripe'). There is no requirement on how soon or what events may occur in between, and a single 'Implement Backend Logic' can fulfill the obligation for all preceding 'Integrate Payment Gateway' events. This defines an ordered flow where backend logic implementation follows payment gateway integration, ensuring a cohesive temporal structure.

2. If a 'Define Project Scope' activity occurs with the activation condition that 'A.Project Status is Delayed,' then a 'Design Database Schema' activity must eventually occur after it, provided the correlation condition 'T.Development Time > 1000' is satisfied. This ensures that when a project is marked as delayed during scope definition, the database schema design must follow, particularly when the development time exceeds 1000 units, maintaining process momentum even under delayed conditions.

3. If an 'Implement Backend Logic' activity occurs with the activation condition that 'A.Payment Method is Credit Card,' then an 'Integrate Payment Gateway' activity must eventually occur after it, provided the correlation condition 'T.Number of Users > 1000' is satisfied, within a time frame between 0 and 1 hour. This ensures a timely integration of the payment gateway following backend logic implementation when credit card payment is selected and the user base exceeds 1000, maintaining the process's momentum.

4. If a 'Deploy Application to Server' activity occurs with the activation condition that 'A.Deployment Environment is Production,' then a 'Monitor System Performance' activity must eventually occur after it, provided the correlation condition 'T.Number of Bugs < 10' is satisfied, within a time frame between 0 and 24 hours. The 'Deploy Application to Server' activity involves transferring the application to a live server environment, linked to the 'Deployment Environment' attribute ('Development,' 'Staging,' or 'Production'). The 'Monitor System Performance' activity encompasses tracking operational metrics, linked to the 'Number of Bugs' attribute (ranging from 0 to 1000). This ensures that production deployments with fewer than 10 bugs are promptly monitored, maintaining operational reliability.

5. If a 'Gather User Feedback' activity occurs with the activation condition that 'A.User Satisfaction < 3,' then an 'Update System Based on Feedback' activity must eventually occur after it, provided the correlation condition 'T.Feedback Type is Bug Report' is satisfied, within a time frame between 0 and 1 day. The 'Gather User Feedback' activity involves collecting opinions and issue reports from users, linked to the 'User Satisfaction' attribute (ranging from 1.0 to 5.0). This ensures that when user satisfaction is low and bug reports are submitted, the system is updated promptly to address user concerns.

6. If a 'Test System Functionality' activity occurs with the activation condition that 'A.Transaction Volume > 1000000,' then an 'Integrate Payment Gateway' activity must eventually occur after it, provided the correlation condition 'T.Number of Users > 10000' is satisfied, within a time frame between 0 and 7 days. This ensures that when testing reveals high transaction volumes and the user base is substantial, the payment gateway is integrated to handle the scale, maintaining system readiness for high-volume operations.

#### **Succession Constraints**
A 'Deploy Application to Server' activity must be followed by a 'Monitor System Performance' activity at some point later in the same process instance. Conversely, a 'Monitor System Performance' event can occur only if a 'Deploy Application to Server' event has occurred before it. This bidirectional and ordered dependency establishes a causal link ensuring that each deployment imposes obligations for future performance monitoring, and each monitoring activity is justified by a preceding deployment. Multiple deployments and monitoring events are allowed, with each deployment eventually leading to monitoring and each monitoring being justified by a prior deployment, creating a cohesive progression within the model.

### **Mutual Dependency Constraints**

#### **Co-Existence Constraints**
If the 'Test System Functionality' activity occurs, then the 'Deploy Application to Server' activity must also occur in the same process instance, and vice-versa. The events can occur multiple times and in any order relative to each other. If neither event occurs, the constraint is still considered satisfied. This mutual dependency ensures that both testing and deployment activities occur together within the process flow, establishing a cohesive relationship between system verification and deployment.

### **Exclusivity Constraints**

#### **Choice Constraints**
At least one of the activities 'Design Database Schema' or 'Develop Frontend Interface' must occur in the process instance. The process is compliant if either 'Design Database Schema' occurs, 'Develop Frontend Interface' occurs, or both occur. There is no restriction on the order or the number of times they occur. However, if neither occurs, the constraint is violated. This introduces alternative paths, allowing flexibility by permitting either activity to occur within the process, thereby accommodating different development approaches.

### **Negative Dependency Constraints**

#### **Not Precedence Constraints**
A 'Gather User Feedback' activity cannot be preceded by a 'Define Project Scope' activity within the same process instance. This means that if any 'Define Project Scope' event has occurred before a 'Gather User Feedback' event, then that 'Gather User Feedback' is disallowed. All instances of 'Gather User Feedback' must occur before any instance of 'Define Project Scope.' This restriction ensures that user feedback gathering does not follow project scope definition, preserving the intended sequence where feedback collection occurs prior to formal project scoping, thereby maintaining the model's defined flow.

#### **Not Response Constraints**
The 'Define Project Scope' activity must not be followed by an 'Update System Based on Feedback' activity at any point later in the same process instance. Once a 'Define Project Scope' event occurs, 'Update System Based on Feedback' cannot occur afterward. However, 'Update System Based on Feedback' events occurring before the 'Define Project Scope' are permitted. This ensures that after the occurrence of project scope definition, the process does not allow any further system updates based on feedback, maintaining the integrity of the model's intended progression by preventing feedback-driven modifications after the project scope has been established.
