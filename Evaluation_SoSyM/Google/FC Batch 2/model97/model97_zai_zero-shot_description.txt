### 1. Activities and Data Context
The model tracks a 10-step software engineering process. Each activity is bound to specific data variables that capture the project's state, resources, and metrics:
*   **Define Project Scope:** Tied to the *Project Status* (Initiated, In Progress, Completed, Delayed).
*   **Design Database Schema:** Tied to *Development Time* (10 to 2000 hours).
*   **Develop Frontend Interface:** Tied to the *Budget Allocated* ($1,000.0 to $500,000.0).
*   **Implement Backend Logic:** Tied to the *Payment Method* (Credit Card, PayPal, Stripe).
*   **Integrate Payment Gateway:** Tied to the *Number of Users* (0 to 1,000,000).
*   **Test System Functionality:** Tied to *Transaction Volume* ($0.0 to $10,000,000.0).
*   **Deploy Application to Server:** Tied to the *Deployment Environment* (Development, Staging, Production).
*   **Monitor System Performance:** Tied to the *Number of Bugs* (0 to 1000).
*   **Gather User Feedback:** Tied to *User Satisfaction* (1.0 to 5.0 rating).
*   **Update System Based on Feedback:** Tied to the *Feedback Type* (Bug Report, Feature Request, Improvement Suggestion).

### 2. Standard Process Constraints (Unconditional Rules)
Regardless of the data generated during execution, the following behavioral rules must always be obeyed:

*   **Ordering:** *Design Database Schema* must occur before *Develop Frontend Interface*. 
*   **Choice:** At exactly one point in the process, a choice must be made to execute either *Design Database Schema* or *Develop Frontend Interface*.
*   **Response:** If *Implement Backend Logic* occurs, *Integrate Payment Gateway* must eventually follow.
*   **Co-Existence:** *Test System Functionality* and *Deploy Application to Server* must always occur together. If one happens, the other must happen as well.
*   **Succession:** If *Deploy Application to Server* occurs, *Monitor System Performance* must eventually follow, and vice versa (a strict order is established between the two).
*   **Negative Relations:** *Gather User Feedback* is strictly forbidden from preceding *Define Project Scope*. Furthermore, *Define Project Scope* can never trigger or be followed by *Update System Based on Feedback*.
*   **Existence/Absence:** *Update System Based on Feedback* must occur at least once during the process. Conversely, *Test System Functionality* is restricted by an absence constraint, meaning it cannot be executed more than 4 times (a maximum of 4 occurrences).
