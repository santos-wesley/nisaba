#MP-Declare Model
## Activities
- **Detect Fraudulent Activity**: The 'Detect Fraudulent Activity' activity involves identifying potentially fraudulent transactions or behaviors within the system.
- **Verify Customer Identity**: The 'Verify Customer Identity' activity includes confirming the identity of a customer through verification attempts and status checks.
- **Review Transaction Details**: The 'Review Transaction Details' activity involves examining the specifics of a transaction, such as its type and amount, for validation purposes.
- **Approve Transaction**: The 'Approve Transaction' activity represents the authorization of a transaction after all necessary checks and verifications have been completed.
- **Decline Transaction**: The 'Decline Transaction' activity involves rejecting a transaction based on failed verification, fraud detection, or other disqualifying criteria.
- **Report Suspicious Activity**: The 'Report Suspicious Activity' activity includes documenting and escalating any suspicious transactions or behaviors to the appropriate authorities or teams.
- **Update Account Security**: The 'Update Account Security' activity involves modifying or enhancing the security settings and measures associated with a customer's account.
- **Notify Customer**: The 'Notify Customer' activity includes informing the customer about transaction outcomes, security alerts, or other relevant account events.
- **Investigate Security Breach**: The 'Investigate Security Breach' activity involves examining and analyzing a security breach to determine its scope, impact, and root cause.
- **Implement Security Patch**: The 'Implement Security Patch' activity represents the application of a security patch to address vulnerabilities identified during a security breach investigation.

## Attributes
- **Transaction Type: Debit, Credit, Wire Transfer, Online Payment**: The attribute 'Transaction Type: Debit, Credit, Wire Transfer, Online Payment' specifies the types of transactions that can be processed within the system.
- **Transaction Amount: float between 0.01 and 100000.0**: The attribute 'Transaction Amount: float between 0.01 and 100000.0' represents the monetary value of a transaction, ranging from 0.01 to 100000.0.
- **Fraud Risk Level: Low, Medium, High**: The attribute 'Fraud Risk Level: Low, Medium, High' indicates the assessed risk level of a transaction being fraudulent.
- **Verification Attempts: integer between 1 and 5**: The attribute 'Verification Attempts: integer between 1 and 5' represents the number of attempts made to verify a customer's identity, ranging from 1 to 5.
- **Verification Status: Verified, Not Verified, Pending**: The attribute 'Verification Status: Verified, Not Verified, Pending' specifies the current status of a customer's identity verification process.
- **Breach Severity: integer between 1 and 10**: The attribute 'Breach Severity: integer between 1 and 10' represents the severity level of a security breach, ranging from 1 to 10.
- **Security Patch Status: Applied, Not Applied, Scheduled**: The attribute 'Security Patch Status: Applied, Not Applied, Scheduled' indicates the current status of a security patch, whether it has been applied, not applied, or scheduled for application.
- **Customer Notification Method: Email, SMS, Phone Call**: The attribute 'Customer Notification Method: Email, SMS, Phone Call' specifies the method used to notify a customer about relevant account events or alerts.
- **Days Since Last Activity: integer between 0 and 365**: The attribute 'Days Since Last Activity: integer between 0 and 365' represents the number of days that have passed since the last account activity, ranging from 0 to 365.

## Interleaved Description
The MP-Declare process model for the fraud detection and security management process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Detect Fraudulent Activity,' which involves identifying potentially fraudulent transactions or behaviors within the system. This activity requires the attributes 'Transaction Type,' 'Transaction Amount,' and 'Fraud Risk Level' to be specified, establishing the initial context for fraud detection and risk assessment.

#### **End Constraints**
The process concludes with the activity 'Implement Security Patch,' which represents the application of a security patch to address vulnerabilities identified during a security breach investigation. This activity must be the last to occur in the process and is associated with the 'Security Patch Status' attribute, ensuring that all security vulnerabilities are addressed before the process is completed.

### **Frequency Constraints**

#### **Absence Constraints**
The 'Detect Fraudulent Activity' activity must not occur 5 times in the process. This restriction highlights the exclusions and reinforces process integrity by specifying that the system should not repeatedly detect fraudulent activity, indicating that effective measures should be in place to prevent recurring fraud attempts.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
The activity 'Verify Customer Identity' is permitted to occur only if an 'Approve Transaction' activity has occurred before it within the same process instance. Any 'Verify Customer Identity' that occurs without a prior 'Approve Transaction' is a violation of the constraint. Multiple 'Approve Transaction' activities can occur, and any number of events can happen between an 'Approve Transaction' and a subsequent 'Verify Customer Identity.' This sets up an initial context where the approval of a transaction must precede the verification of customer identity, guiding the logical sequence within the model and ensuring that certain actions cannot proceed without the necessary prerequisites being met first.

#### **Response Constraints**
1. If a 'Detect Fraudulent Activity' activity occurs, then a 'Notify Customer' activity must eventually occur after the 'Detect Fraudulent Activity' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Detect Fraudulent Activity' events can be pending at the same time, and a single 'Notify Customer' can fulfill the obligation for all preceding 'Detect Fraudulent Activity' events. This defines an ordered flow where customer notification follows fraud detection, ensuring a cohesive temporal structure in the model.

2. If a 'Decline Transaction' activity occurs, then a 'Report Suspicious Activity' activity must eventually occur after the 'Decline Transaction' event at some point in the same process instance.
