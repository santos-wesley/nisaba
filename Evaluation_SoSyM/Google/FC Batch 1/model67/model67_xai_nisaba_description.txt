#MP-Declare Model
## Activities
- **Detect Fraudulent Activity**: The 'Detect Fraudulent Activity' activity represents the detection of potentially fraudulent transactions in the system.
- **Verify Customer Identity**: The 'Verify Customer Identity' activity involves confirming the identity of the customer associated with the transaction.
- **Review Transaction Details**: The 'Review Transaction Details' activity includes examining the specifics of the transaction for any anomalies.
- **Approve Transaction**: The 'Approve Transaction' activity signifies the approval of a verified and legitimate transaction.
- **Decline Transaction**: The 'Decline Transaction' activity indicates the rejection of a suspicious or invalid transaction.
- **Report Suspicious Activity**: The 'Report Suspicious Activity' activity involves documenting and reporting any detected suspicious behavior.
- **Update Account Security**: The 'Update Account Security' activity focuses on enhancing the security measures of the customer's account.
- **Notify Customer**: The 'Notify Customer' activity entails informing the customer about transaction status or security issues.
- **Investigate Security Breach**: The 'Investigate Security Breach' activity involves a thorough investigation into any potential security breaches.
- **Implement Security Patch**: The 'Implement Security Patch' activity represents the application of necessary security updates or patches.

## Attributes
- **Transaction Type: Debit, Credit, Wire Transfer, Online Payment**: The attribute 'Transaction Type: Debit, Credit, Wire Transfer, Online Payment' specifies the various methods through which a transaction can be conducted.
- **Transaction Amount: float between 0.01 and 100000.0**: The attribute 'Transaction Amount: float between 0.01 and 100000.0' represents the monetary value of the transaction within the specified range.
- **Fraud Risk Level: Low, Medium, High**: The attribute 'Fraud Risk Level: Low, Medium, High' indicates the assessed level of risk associated with the transaction.
- **Verification Attempts: integer between 1 and 5**: The attribute 'Verification Attempts: integer between 1 and 5' tracks the number of attempts made to verify the customer's identity.
- **Verification Status: Verified, Not Verified, Pending**: The attribute 'Verification Status: Verified, Not Verified, Pending' reflects the current state of the customer identity verification process.
- **Breach Severity: integer between 1 and 10**: The attribute 'Breach Severity: integer between 1 and 10' quantifies the severity level of a detected security breach.
- **Security Patch Status: Applied, Not Applied, Scheduled**: The attribute 'Security Patch Status: Applied, Not Applied, Scheduled' denotes the current status of security patch implementation.
- **Customer Notification Method: Email, SMS, Phone Call**: The attribute 'Customer Notification Method: Email, SMS, Phone Call' specifies the preferred method for notifying the customer.
- **Days Since Last Activity: integer between 0 and 365**: The attribute 'Days Since Last Activity: integer between 0 and 365' measures the number of days elapsed since the last account activity.

## Interleaved Description
The MP-Declare process model for the fraud detection and security management process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins once a transaction is initiated in the system, establishing the initial context for monitoring activities such as 'Detect Fraudulent Activity' (with attributes Transaction Type, Transaction Amount, and Fraud Risk Level), 'Review Transaction Details' (with attributes Transaction Type and Transaction Amount), and 'Verify Customer Identity' (with attributes Verification Attempts and Verification Status).

### **Frequency Constraints**

#### **Absence Constraints**
In contrast to allowing unlimited detections, the 'Detect Fraudulent Activity' must not occur 5 times in the process. This exclusion reinforces process integrity by specifying that repeated fraudulent detections beyond this threshold are not permissible, preventing excessive alerts within a single instance.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
The 'Verify Customer Identity' activity is permitted to occur only if an 'Approve Transaction' activity has occurred before it within the same process instance. This background establishes the initial context that approval must precede verification, guiding the logical sequence so that identity checks are grounded in a prior legitimate approval decision.

#### **Response Constraints**
1. If a 'Detect Fraudulent Activity' activity occurs, then a 'Notify Customer' activity must eventually occur after the 'Detect Fraudulent Activity' event at some point in the same process instance. This sequence defines an ordered flow where detection leads to customer notification, ensuring a cohesive temporal structure regardless of intervening events.
2. If a 'Decline Transaction' activity occurs, then a 'Report Suspicious Activity' activity must eventually occur after the 'Decline Transaction' event at some point in the same process instance. This sequence ensures that every declined transaction is followed by proper reporting, maintaining procedural coherence.
3. If an 'Investigate Security Breach' activity occurs, then an 'Implement Security Patch' activity must eventually occur after the 'Investigate Security Breach' event at some point in the same process instance within a time frame between 0 and 72 hours. This sequence creates a time-bound ordered flow from investigation to remediation.
4. If a 'Review Transaction Details' activity occurs with the activation condition that 'A.Transaction Amount > 1000', then a 'Verify Customer Identity' activity must eventually occur after the 'Review Transaction Details' event at some point in the same process instance within a time frame between 0 and 10 minutes. This sequence ensures rapid verification for high-value transactions, preserving process momentum.
5. If a 'Detect Fraudulent Activity' activity occurs with the activation condition that 'A.Fraud Risk Level is High', then a 'Decline Transaction' activity must eventually occur after the 'Detect Fraudulent Activity' event at some point in the same process instance within a time frame between 0 and 5 minutes. This sequence enforces swift action on high-risk detections, creating a tight temporal structure.
6. If a 'Notify Customer' activity occurs with the activation condition that 'A.Customer Notification Method is SMS', then an 'Update Account Security' activity must eventually occur after the 'Notify Customer' event at some point in the same process instance within a time frame between 0 and 24 hours. This sequence links SMS-based alerts directly to security enhancements.
7. If an 'Investigate Security Breach' activity occurs with the activation condition that 'A.Breach Severity > 7', then an 'Implement Security Patch' activity must eventually occur after the 'Investigate Security Breach' event at some point in the same process instance within a time frame between 0 and 48 hours. This sequence accelerates patching for severe breaches.
8. If an 'Implement Security Patch' activity occurs with the activation condition that 'A.Security Patch Status is Not Applied', then an 'Implement Security Patch' activity must eventually occur after the 'Implement Security Patch' event at some point in the same process instance within a time frame between 0 and 7 days. This sequence ensures repeated implementation attempts until the patch status advances.

### **Immediate Ordering Constraints**

#### **Chain Succession Constraints**
The model applies a tightly coupled sequence between 'Implement Security Patch' activities when the patch remains Not Applied. This cause-effect relationship enforces that each activation with 'Security Patch Status is Not Applied' is directly succeeded by another implementation attempt within 7 days, with no intervening activities, thereby maintaining continuous security remediation without gaps. 

The process concludes with the activity 'Approve Transaction' or 'Decline Transaction' (both bound to Transaction Type and Transaction Amount), which finalizes the handling of the monitored transaction and ensures all dependent security and notification obligations are resolved.
