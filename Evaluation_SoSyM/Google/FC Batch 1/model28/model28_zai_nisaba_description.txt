#MP-Declare Model
## Activities
- **Submit Application**: The 'Submit Application' activity represents the initial step where an individual submits a work arrangement application.
- **Review Application**: The 'Review Application' activity involves evaluating a submitted application to determine its suitability.
- **Approve Application**: The 'Approve Application' activity represents the formal approval of a reviewed application, allowing it to proceed to implementation.
- **Reject Application**: The 'Reject Application' activity represents the formal rejection of a reviewed application, preventing it from proceeding further.
- **Implement Arrangement**: The 'Implement Arrangement' activity involves putting an approved work arrangement into practice.
- **Monitor Arrangement**: The 'Monitor Arrangement' activity entails overseeing an implemented work arrangement to ensure it functions as intended.
- **Adjust Arrangement**: The 'Adjust Arrangement' activity involves modifying an existing work arrangement based on monitoring outcomes.
- **Terminate Arrangement**: The 'Terminate Arrangement' activity represents the formal ending of an active work arrangement.

## Attributes
- **Arrangement Type: Remote Work, Flextime, Compressed Workweek, Job Sharing**: The attribute 'Arrangement Type: Remote Work, Flextime, Compressed Workweek, Job Sharing' specifies the possible types of work arrangements that can be requested in an application.
- **Application ID: integer between 1 and 1000**: The attribute 'Application ID: integer between 1 and 1000' represents the unique identification number assigned to each application.
- **Application Status: Submitted, Reviewed, Approved, Rejected, Implemented, Terminated**: The attribute 'Application Status: Submitted, Reviewed, Approved, Rejected, Implemented, Terminated' specifies the possible statuses an application can have throughout its lifecycle.
- **Hours Per Week: float between 10.0 and 40.0**: The attribute 'Hours Per Week: float between 10.0 and 40.0' represents the number of weekly hours associated with a work arrangement.
- **Review Score: integer between 1 and 5**: The attribute 'Review Score: integer between 1 and 5' represents the score assigned to an application during the review process.

- **Review Application: Application ID, Application Status, Review Score**: The bind 'Review Application: Application ID, Application Status, Review Score' links the 'Review Application' activity with the attributes 'Application ID', 'Application Status', and 'Review Score'.
- **Approve Application: Application ID, Application Status**: The bind 'Approve Application: Application ID, Application Status' links the 'Approve Application' activity with the attributes 'Application ID' and 'Application Status'.
- **Reject Application: Application ID, Application Status**: The bind 'Reject Application: Application ID, Application Status' links the 'Reject Application' activity with the attributes 'Application ID' and 'Application Status'.
- **Implement Arrangement: Application ID, Application Status, Hours Per Week**: The bind 'Implement Arrangement: Application ID, Application Status, Hours Per Week' links the 'Implement Arrangement' activity with the attributes 'Application ID', 'Application Status', and 'Hours Per Week'.
- **Monitor Arrangement: Application ID**: The bind 'Monitor Arrangement: Application ID' links the 'Monitor Arrangement' activity with the attribute 'Application ID'.
- **Adjust Arrangement: Application ID, Hours Per Week**: The bind 'Adjust Arrangement: Application ID, Hours Per Week' links the 'Adjust Arrangement' activity with the attributes 'Application ID' and 'Hours Per Week'.

## Interleaved Description
The MP-Declare process model for the work arrangement management process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Submit Application,' which involves an individual submitting a work arrangement application with 'Arrangement Type' and 'Application ID' attributes. This activity must be the first to occur in the process, establishing the initial context for the entire workflow.

### **Frequency Constraints**

#### **Existence Constraint**
The process does not impose specific existence constraints beyond the initial submission; however, the presence of activities throughout the process is governed by the various dependency and ordering constraints described below, adding depth and context to the process model.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
The activity 'Review Application' is permitted to occur only if an 'Approve Application' activity has occurred before it within the same process instance. This ensures that the 'Review Application' cannot proceed without the necessary prerequisite 'Approve Application' being met first. Multiple 'Approve Application' events can occur, and any number of events can happen between an 'Approve Application' and a subsequent 'Review Application,' setting up an initial context where approval logically precedes review.

#### **Response Constraints**
1. If a 'Submit Application' activity occurs, then a 'Review Application' activity must eventually occur after the 'Submit Application' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Submit Application' events can be pending at the same time, and a single 'Review Application' can fulfill the obligation for all preceding 'Submit Application' events. This defines an ordered flow where review follows submission, ensuring a cohesive temporal structure in the model.
2. If an 'Approve Application' activity occurs, then an 'Implement Arrangement' activity must eventually occur after the 'Approve Application' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Approve Application' events can be pending at the same time, and a single 'Implement Arrangement' can fulfill the obligation for all preceding 'Approve Application' events. This ensures that approved applications are eventually implemented, maintaining the process's forward momentum.
3. If a 'Monitor Arrangement' activity occurs, then an 'Adjust Arrangement' activity must eventually occur after the 'Monitor Arrangement' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Monitor Arrangement' events can be pending at the same time, and a single 'Adjust Arrangement' can fulfill the obligation for all preceding 'Monitor Arrangement' events. This ensures that monitoring leads to potential adjustments, maintaining the process's adaptive nature.
4. If an 'Approve Application' activity occurs with the activation condition 'A.Application Status is Approved,' then a 'Terminate Arrangement' activity must eventually occur after the 'Approve Application' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Approve Application' events can be pending at the same time, and a single 'Terminate Arrangement' can fulfill the obligation for all preceding 'Approve Application' events. This constraint only applies when the application status of the 'Approve Application' activation event is 'Approved,' ensuring that approved arrangements are eventually terminated.

#### **Succession Constraints**
An 'Implement Arrangement' activity must be followed by a 'Monitor Arrangement' activity at some point later in the same process instance. Conversely, a 'Monitor Arrangement' event can occur only if an 'Implement Arrangement' event has occurred before it within the same process instance. This bidirectional and ordered dependency establishes a causal link, ensuring that 'Implement Arrangement' imposes obligations for future 'Monitor Arrangement,' and 'Monitor Arrangement' cannot occur without prior 'Implement Arrangement.' Multiple 'Implement Arrangement' and 'Monitor Arrangement' events are allowed, with each 'Implement Arrangement' eventually leading to a 'Monitor Arrangement' and each 'Monitor Arrangement' being justified by a preceding 'Implement Arrangement,' creating a cohesive progression within the model.

### **Exclusivity Constraints**

#### **Choice Constraints**
At least one of the activities 'Approve Application' or 'Reject Application' must occur in the process instance. This means that the process is compliant if 'Approve Application' occurs, 'Reject Application' occurs, or both occur. There is no restriction on the order or the number of times they occur. However, if neither 'Approve Application' nor 'Reject Application' occurs, the constraint is violated. This introduces alternative paths, allowing flexibility by permitting either activity to occur within the process.

#### **Not Co-Existence Constraints**
The 'Submit Application' activity and the 'Review Application' activity cannot both occur within the same process instance. This means that if 'Submit Application' occurs one or more times, 'Review Application' must not occur at all in that process instance, and vice-versa. It is acceptable for neither event to occur. This exclusion enforces a mutual exclusion between 'Submit Application' and 'Review Application,' maintaining process integrity by preventing conflicting events and allowing for different process variants based on which event, if any, occurs.

### **Negative Flexible Ordering Constraints**

#### **Not Response Constraints**
The 'Reject Application' activity must not be followed by a 'Terminate Arrangement' activity at any point later in the same process instance, with the activation condition 'A.Application Status is Rejected.' This means that once a 'Reject Application' event occurs with the application status 'Rejected,' 'Terminate Arrangement' cannot occur afterward. However, 'Terminate Arrangement' events occurring before the 'Reject Application' are permitted. This constraint ensures that after the occurrence of 'Reject Application' with the specified condition, the process does not allow any further occurrences of 'Terminate Arrangement,' thereby maintaining the integrity of the model's intended progression by preventing rejected applications from leading to arrangement termination.
