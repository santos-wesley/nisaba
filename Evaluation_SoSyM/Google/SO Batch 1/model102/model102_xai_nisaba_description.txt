#MP-Declare Model
## Activities
- **Submit Timesheet**: The 'Submit Timesheet' activity represents the initial submission of employee work hours for payroll processing.
- **Approve Timesheet**: The 'Approve Timesheet' activity involves reviewing and approving the submitted timesheet by a supervisor or manager.
- **Calculate Gross Pay**: The 'Calculate Gross Pay' activity computes the total earnings before any deductions based on hours worked and pay rate.
- **Calculate Deductions**: The 'Calculate Deductions' activity determines the amounts to be subtracted from gross pay, including taxes and insurance.
- **Calculate Net Pay**: The 'Calculate Net Pay' activity computes the final take-home pay after subtracting all deductions from the gross pay.
- **Generate Paystub**: The 'Generate Paystub' activity creates a detailed pay statement for the employee showing earnings and deductions.
- **Process Payment**: The 'Process Payment' activity handles the actual disbursement of net pay to the employee via the selected method.
- **Update Payroll Records**: The 'Update Payroll Records' activity records the payroll transaction details in the company's financial system.
- **Review Payroll Report**: The 'Review Payroll Report' activity involves examining the generated payroll summary for accuracy and compliance.
- **Distribute Paystub**: The 'Distribute Paystub' activity sends or provides the paystub to the employee for their records.

## Attributes
- **Hours Worked: integer between 0 and 80**: The attribute 'Hours Worked: integer between 0 and 80' represents the number of hours an employee has worked in a pay period, ranging from 0 to 80.
- **Pay Rate: float between 10.0 and 100.0**: The attribute 'Pay Rate: float between 10.0 and 100.0' represents the hourly wage rate for the employee, ranging from 10.0 to 100.0.
- **Gross Pay: float between 0.0 and 10000.0**: The attribute 'Gross Pay: float between 0.0 and 10000.0' represents the total earnings before deductions, ranging from 0.0 to 10000.0.
- **Tax Deduction: float between 0.0 and 5000.0**: The attribute 'Tax Deduction: float between 0.0 and 5000.0' represents the amount deducted for taxes, ranging from 0.0 to 5000.0.
- **Insurance Deduction: float between 0.0 and 1000.0**: The attribute 'Insurance Deduction: float between 0.0 and 1000.0' represents the amount deducted for insurance, ranging from 0.0 to 1000.0.
- **Net Pay: float between 0.0 and 10000.0**: The attribute 'Net Pay: float between 0.0 and 10000.0' represents the final amount paid to the employee after deductions, ranging from 0.0 to 10000.0.
- **Timesheet Status: Submitted, Approved, Rejected**: The attribute 'Timesheet Status: Submitted, Approved, Rejected' specifies the current status of the timesheet, which can be Submitted, Approved, or Rejected.
- **Payment Method: Direct Deposit, Check**: The attribute 'Payment Method: Direct Deposit, Check' indicates the method used to disburse payment, which can be Direct Deposit or Check.
- **Employee ID: integer between 1000 and 9999**: The attribute 'Employee ID: integer between 1000 and 9999' represents the unique identification number for an employee, ranging from 1000 to 9999.

## Interleaved Description
The MP-Declare process model for the payroll processing is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Submit Timesheet,' which involves the initial submission of employee work hours for payroll processing with the 'Employee ID,' 'Hours Worked,' and 'Timesheet Status' attributes. This activity must be the first to occur in the process.

### **Flexible Ordering Constraints**

#### **Response Constraints**
1. If the 'Submit Timesheet' activity occurs, then the 'Approve Timesheet' activity must eventually occur after it. This establishes an ordered flow where the approval follows the submission, ensuring a cohesive temporal structure in the model as the 'Timesheet Status' transitions from Submitted toward Approved.
2. If the 'Approve Timesheet' activity occurs, then the 'Calculate Gross Pay' activity must eventually occur after it. This defines an ordered flow where gross pay computation follows approval, maintaining process momentum once the timesheet has been reviewed and the 'Timesheet Status' is set to Approved.
3. If the 'Calculate Gross Pay' activity occurs with the 'Hours Worked,' 'Pay Rate,' and resulting 'Gross Pay' attributes, then the 'Calculate Deductions' activity must eventually occur after it. This sequences the determination of 'Tax Deduction' and 'Insurance Deduction' amounts directly after gross earnings are known.
4. If the 'Calculate Deductions' activity occurs, then the 'Calculate Net Pay' activity must eventually occur after it. This ordered flow computes the final 'Net Pay' by subtracting all deductions from 'Gross Pay,' ensuring logical progression in the payroll calculations.
5. If the 'Calculate Net Pay' activity occurs, then the 'Process Payment' activity must eventually occur after it. This ensures the disbursement via the selected 'Payment Method' (Direct Deposit or Check) follows net pay computation for the given 'Employee ID.'
6. If the 'Process Payment' activity occurs, then the 'Update Payroll Records' activity must eventually occur after it. This sequences the recording of transaction details in the company's financial system immediately after payment handling.
7. If the 'Update Payroll Records' activity occurs, then the 'Review Payroll Report' activity must eventually occur after it. This ordered flow allows examination of the generated payroll summary for accuracy and compliance.
8. If the 'Process Payment' activity occurs, then the 'Distribute Paystub' activity must eventually occur after it within a 0-to-24-hour window. This ensures the detailed pay statement showing earnings and deductions is sent to the employee promptly after disbursement.

#### **Not Response Constraints**
The 'Approve Timesheet' activity must not be followed by a 'Submit Timesheet' activity at any point later in the same process instance when the 'Timesheet Status' is Rejected. This contrast prevents any further submission once rejection has been recorded, thereby maintaining the integrity of the model's intended progression and avoiding rework loops after a final decision.

### **Immediate Ordering Constraints**

#### **Chain Succession Constraints**
The tightly coupled sequence between approval and subsequent calculations is implicitly supported by the chained response obligations; however, no explicit immediate succession without intervening activities is mandated beyond the overall payroll flow. The model relies on the response chain to create a cohesive progression from submission through payment and record updating.
