#MP-Declare Model
## Activities
- **Schedule Train**: The 'Schedule Train' activity represents the process of scheduling a train for its planned route.
- **Allocate Resources**: The 'Allocate Resources' activity involves assigning necessary resources such as tracks and equipment to a train.
- **Monitor Train**: The 'Monitor Train' activity involves tracking the status and progress of a train during its journey.
- **Manage Delay**: The 'Manage Delay' activity involves handling and mitigating any delays encountered by a train.
- **Perform Maintenance**: The 'Perform Maintenance' activity involves carrying out maintenance tasks on a train.
- **Inspect Track**: The 'Inspect Track' activity involves examining the condition of railway tracks.
- **Dispatch Train**: The 'Dispatch Train' activity involves sending a train out on its scheduled route.
- **Receive Train**: The 'Receive Train' activity involves accepting a train upon its arrival at a station.
- **Update Schedule**: The 'Update Schedule' activity involves modifying the train schedule as needed.
- **Cancel Train**: The 'Cancel Train' activity involves canceling a train's scheduled service.

## Attributes
- **Train ID: integer between 1000 and 9999**: The attribute 'Train ID: integer between 1000 and 9999' represents the unique identification number assigned to each train.
- **Train Status: On Time, Delayed, Cancelled, Completed**: The attribute 'Train Status: On Time, Delayed, Cancelled, Completed' specifies the current operational status of a train.
- **Delay Duration: float between 0.0 and 300.0**: The attribute 'Delay Duration: float between 0.0 and 300.0' represents the length of time a train is delayed, measured in minutes.
- **Track Number: integer between 1 and 10**: The attribute 'Track Number: integer between 1 and 10' represents the identifier of the railway track assigned to a train.
- **Maintenance Type: Routine, Emergency, Scheduled**: The attribute 'Maintenance Type: Routine, Emergency, Scheduled' specifies the category of maintenance to be performed on a train.
- **Inspection Score: float between 0.0 and 10.0**: The attribute 'Inspection Score: float between 0.0 and 10.0' represents the quality rating resulting from a track inspection.
- **Priority Level: High, Medium, Low**: The attribute 'Priority Level: High, Medium, Low' specifies the urgency level assigned to a train dispatch.
- **Passenger Count: integer between 0 and 1500**: The attribute 'Passenger Count: integer between 0 and 1500' represents the number of passengers on board a train upon arrival.
- **Reason Cancel: Weather, Maintenance, Technical Issue**: The attribute 'Reason Cancel: Weather, Maintenance, Technical Issue' specifies the reason for canceling a train service.
- **Schedule Version: integer between 1 and 100**: The attribute 'Schedule Version: integer between 1 and 100' represents the version number of the train schedule.

## Constraints
- **Init[Schedule Train] | |**: The 'Schedule Train' must be the first activity to occur in the process.
- **Precedence[Dispatch Train, Allocate Resources] | | |**: The 'Allocate Resources' activity is permitted to occur only if a 'Dispatch Train' activity has occurred before it within the same process instance.
- **Response[Monitor Train, Manage Delay] |A.Train Status is Delayed | |**: If a 'Monitor Train' activity occurs and its 'Train Status' attribute is 'Delayed', then a 'Manage Delay' activity must eventually occur after the 'Monitor Train' event at some point in the same process instance. There is no requirement on how soon or what events may occur in between. Multiple 'Monitor Train' can be pending at the same time, and a single 'Manage Delay' can fulfill the obligation for all preceding 'Monitor Train'. If 'Monitor Train' does not occur, the constraint imposes no obligation on the occurrence of 'Manage Delay'.
- **Chain Precedence[Dispatch Train, Perform Maintenance] | | |**: The 'Perform Maintenance' activity can occur only if it is immediately preceded by 'Dispatch Train' activity, with no other activities occurring in between.
- **Succession[Inspect Track, Allocate Resources] | | |**: An 'Inspect Track' activity must be followed by an 'Allocate Resources' activity at some point later in the same process instance. Conversely, an 'Allocate Resources' event can occur only if an 'Inspect Track' event has occurred before it within the same process instance. This bidirectional and ordered dependency ensures that 'Inspect Track' impose obligations for future 'Allocate Resources', and 'Allocate Resources' cannot occur without prior 'Inspect Track'. Multiple 'Inspect Track' and 'Allocate Resources' are allowed, with each 'Inspect Track' eventually leading to an 'Allocate Resources' and each 'Allocate Resources' being justified by a preceding 'Inspect Track'.
- **Responded Existence[Dispatch Train, Receive Train] | | |**: If 'Dispatch Train' activity occurs in a process instance, then 'Receive Train' activity must also occur at least once within the same process instance, either before or after the 'Dispatch Train' event. If 'Dispatch Train' does not occur, there is no requirement for 'Receive Train' to occur. Multiple occurrences of 'Dispatch Train' are satisfied by at least one occurrence of 'Receive Train', and multiple 'Receive Train' instances are allowed.
- **Not Co-Existence[Dispatch Train, Cancel Train] | | |**: The 'Dispatch Train' activity and the 'Cancel Train' activity cannot both occur within the same process instance. This means that if 'Dispatch Train' event occurs one or more times, 'Cancel Train' must not occur at all in that process instance, and vice-versa. It is acceptable for neither event to occur. The constraint enforces a mutual exclusion between 'Dispatch Train' and 'Cancel Train', allowing for different process variants based on which event (if any) occurs.
- **Not Chain Succession[Update Schedule, Schedule Train] | | |**: An 'Update Schedule' activity cannot be immediately followed by a 'Schedule Train' activity; there must be at least one other event between them. Similarly, a 'Schedule Train' event cannot be immediately preceded by an 'Update Schedule' event. This constraint allows multiple occurrences of 'Update Schedule' and 'Schedule Train' in any order, provided they are not adjacent in the event sequence.
- **Choice[Dispatch Train, Cancel Train] | | |**: At least one of the activities 'Dispatch Train' or 'Cancel Train' must occur in the process instance. This means that the process is compliant if 'Dispatch Train' event occurs, 'Cancel Train' event occurs, or both occur. There is no restriction on the order or the number of times they occur. However, if neither 'Dispatch Train' nor 'Cancel Train' occurs, the constraint is violated.
- **Absence2[Cancel Train] | |**: The 'Cancel Train' must not occur 2 times in the process.


## Interleaved Description
The MP-Declare process model for the train operations process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Schedule Train,' which involves scheduling a train for its planned route, capturing the unique 'Train ID' and the 'Schedule Version' to establish the initial context for the entire process.

### **Frequency Constraints**
#### **Absence Constraints**
In contrast to the possibility of multiple cancellations, the 'Cancel Train' activity must not occur 2 times in the process. This exclusion reinforces process integrity by limiting the frequency of cancellations, ensuring that a train service is not arbitrarily terminated more than once.

### **Dependency Constraints**
#### **Responded Existence Constraints**
If a 'Dispatch Train' activity occurs, it causes the necessity of a 'Receive Train' activity occurring at least once within the same process instance, either before or after the dispatch. This cause-effect relationship ensures that every dispatched train is eventually accounted for upon arrival, enhancing coherence in the process flow.

### **Flexible Ordering Constraints**
#### **Precedence Constraints**
The 'Allocate Resources' activity is permitted to occur only if a 'Dispatch Train' activity has occurred before it. This background condition ensures that resources such as tracks and equipment are assigned only after a train has been dispatched, guiding the logical sequence within the model.

#### **Response Constraints**
If a 'Monitor Train' activity occurs and its 'Train Status' attribute is 'Delayed,' then a 'Manage Delay' activity must eventually occur after the monitoring event. This sequence defines an ordered flow where delay management follows the detection of a delay, ensuring a cohesive temporal structure in handling train disruptions.

#### **Succession Constraints**
An 'Inspect Track' activity must be followed by an 'Allocate Resources' activity at some point later, and conversely, an 'Allocate Resources' event can occur only if an 'Inspect Track' event has occurred before it. This cause-effect link ensures that track inspections logically lead to resource allocation, creating a cohesive progression where each allocation is justified by a prior inspection.

### **Exclusivity Constraints**
#### **Choice Constraints**
At least one of the activities 'Dispatch Train' or 'Cancel Train' must occur in the process instance. This contrast introduces alternative paths, allowing flexibility by permitting either dispatching a train or canceling its service, ensuring that the process always moves toward a definitive outcome.

#### **Not Co-Existence Constraints**
The 'Dispatch Train' activity and the 'Cancel Train' activity cannot both occur within the same process instance. This contrast sets an exclusion rule, ensuring that a train cannot be both dispatched and canceled in the same instance, thereby maintaining process integrity by preventing these conflicting events.

### **Immediate Ordering Constraints**
#### **Chain Precedence Constraints**
The 'Perform Maintenance' activity can occur only if it is immediately preceded by 'Dispatch Train' activity, with no other activities occurring in between. This sequence establishes an immediate dependency, ensuring that maintenance tasks follow directly after a train is dispatched, making the sequence explicit and precise.

### **Negative Immediate Ordering Constraints**
#### **Not Chain Succession Constraints**
An 'Update Schedule' activity cannot be immediately followed by a 'Schedule Train' activity; there must be at least one other event between them. Similarly, a 'Schedule Train' event cannot be immediately preceded by an 'Update Schedule' event. This contrast prevents direct succession, ensuring that schedule updates and initial scheduling are not adjacent, thereby refining the process model by excluding specific immediate sequences.
