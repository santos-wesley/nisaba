#MP-Declare Model
## Activities
- **Identify Needs**: The 'Identify Needs' activity represents the initial phase of determining the requirements and needs of the organization.
- **Select Vendor**: The 'Select Vendor' activity involves choosing a suitable vendor based on the identified needs.
- **Negotiate Contract**: The 'Negotiate Contract' activity involves discussing terms and conditions with the selected vendor.
- **Sign Contract**: The 'Sign Contract' activity represents the formal signing of the agreement with the vendor.
- **Monitor Performance**: The 'Monitor Performance' activity involves tracking and evaluating the vendor's performance over time.
- **Review Compliance**: The 'Review Compliance' activity involves checking whether the vendor adheres to regulatory and contractual requirements.
- **Issue Payment**: The 'Issue Payment' activity involves processing and disbursing payment to the vendor.
- **Conduct Review**: The 'Conduct Review' activity involves performing a final evaluation of the vendor's overall performance and outcomes.

## Attributes
- **Vendor ID: integer between 1 and 9999**: The attribute 'Vendor ID: integer between 1 and 9999' represents the unique identification number assigned to each vendor.
- **Vendor Name: Vendor A, Vendor B, Vendor C**: The attribute 'Vendor Name: Vendor A, Vendor B, Vendor C' specifies the possible names of vendors available for selection.
- **Contract Amount: integer between 1000 and 1000000**: The attribute 'Contract Amount: integer between 1000 and 1000000' represents the monetary value of the contract negotiated with the vendor.
- **KPI Score: float between 0.0 and 10.0**: The attribute 'KPI Score: float between 0.0 and 10.0' represents the key performance indicator score used to evaluate vendor performance.
- **Compliance Status: Compliant, Non-Compliant**: The attribute 'Compliance Status: Compliant, Non-Compliant' indicates whether the vendor meets compliance requirements.
- **Review Outcome: Satisfactory, Unsatisfactory**: The attribute 'Review Outcome: Satisfactory, Unsatisfactory' specifies the result of the vendor review process.
- **Payment Status: Pending, Completed**: The attribute 'Payment Status: Pending, Completed' indicates the current state of the payment issued to the vendor.

## Binds
- **Select Vendor: Vendor ID, Vendor Name**: The bind 'Select Vendor: Vendor ID, Vendor Name' specifies that the activity 'Select Vendor' requires the attributes 'Vendor ID' and 'Vendor Name'.
- **Negotiate Contract: Vendor ID, Contract Amount**: The bind 'Negotiate Contract: Vendor ID, Contract Amount' links the 'Negotiate Contract' activity with the attributes 'Vendor ID' and 'Contract Amount'.
- **Monitor Performance: Vendor ID, KPI Score**: The bind 'Monitor Performance: Vendor ID, KPI Score' links the 'Monitor Performance' activity with the attributes 'Vendor ID' and 'KPI Score'.
- **Review Compliance: Vendor ID, Compliance Status**: The bind 'Review Compliance: Vendor ID, Compliance Status' links the 'Review Compliance' activity with the attributes 'Vendor ID' and 'Compliance Status'.
- **Issue Payment: Vendor ID, Payment Status**: The bind 'Issue Payment: Vendor ID, Payment Status' links the 'Issue Payment' activity with the attributes 'Vendor ID' and 'Payment Status'.
- **Conduct Review: Vendor ID, Review Outcome**: The bind 'Conduct Review: Vendor ID, Review Outcome' links the 'Conduct Review' activity with the attributes 'Vendor ID' and 'Review Outcome'.

## Interleaved Description
The MP-Declare process model for the vendor management process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Identify Needs,' which involves determining the requirements and needs of the organization. This activity sets the initial context for the entire vendor management workflow.
#### **End Constraints**
The process concludes with the activity 'Conduct Review,' which involves performing a final evaluation of the vendor's overall performance and outcomes. This activity must be the last to occur in the process, providing a coherent closure to the model.

### **Frequency Constraints**
#### **Absence Constraint**
In contrast to typical process flows, the 'Select Vendor' activity must not occur in the process. This exclusion reinforces process integrity by specifying that vendor selection is not permissible, likely because the vendor is predetermined or the selection occurs outside this model.

### **Flexible Ordering Constraints**
#### **Precedence Constraints**
1. The activity 'Identify Needs' is permitted to occur only if a 'Select Vendor' activity has occurred before it. This establishes an initial context where vendor selection precedes needs identification, guiding the logical sequence within the model.
2. The activity 'Select Vendor' is permitted to occur only if a 'Negotiate Contract' activity has occurred before it. This sets up a background where contract negotiation must happen before vendor selection, ensuring a coherent ordering of activities.
3. The activity 'Monitor Performance' is permitted to occur only if a 'Review Compliance' activity has occurred before it. This provides context that compliance review must precede performance monitoring, maintaining the intended sequence.
4. The activity 'Review Compliance' is permitted to occur only if an 'Issue Payment' activity has occurred before it. This establishes a background where payment issuance must happen before compliance review, guiding the process flow.

### **Immediate Ordering Constraints**
#### **Chain Response Constraints**
1. Whenever a 'Negotiate Contract' activity occurs, it must be immediately followed by a 'Sign Contract' activity in the next event position, with no other events in between. This must occur within 0 to 7 days. This cause-effect relationship ensures a direct and immediate succession from negotiation to signing, capturing a tightly coupled sequence.
2. Whenever a 'Sign Contract' activity occurs, it must be immediately followed by a 'Monitor Performance' activity in the next event position, with no other events in between. This must occur within 0 to 2 days. This cause-effect link ensures that performance monitoring directly follows contract signing, maintaining a seamless progression.
3. Whenever an 'Issue Payment' activity occurs, it must be immediately followed by a 'Conduct Review' activity in the next event position, with no other events in between. This must occur within 0 to 2 days. This cause-effect relationship ensures that the final review directly follows payment issuance, providing a tightly coupled sequence to conclude the process.
