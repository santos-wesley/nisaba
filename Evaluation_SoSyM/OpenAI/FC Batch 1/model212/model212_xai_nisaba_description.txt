#MP-Declare Model
## Activities
- **Identify Needs**: The 'Identify Needs' activity represents the initial phase where the organization determines its requirements for goods or services.
- **Select Vendor**: The 'Select Vendor' activity involves choosing an appropriate vendor based on the identified needs.
- **Negotiate Contract**: The 'Negotiate Contract' activity includes discussing and agreeing on the terms of the contract with the selected vendor.
- **Sign Contract**: The 'Sign Contract' activity formalizes the agreement by signing the contract with the vendor.
- **Monitor Performance**: The 'Monitor Performance' activity entails ongoing assessment of the vendor's performance against agreed standards.
- **Review Compliance**: The 'Review Compliance' activity involves evaluating whether the vendor adheres to compliance requirements.
- **Issue Payment**: The 'Issue Payment' activity is the process of releasing payment to the vendor upon satisfactory performance.
- **Conduct Review**: The 'Conduct Review' activity includes performing a final review of the vendor's overall performance and outcomes.

## Attributes
- **Vendor ID: integer between 1 and 9999**: The attribute 'Vendor ID: integer between 1 and 9999' represents a unique numerical identifier assigned to each vendor, ranging from 1 to 9999.
- **Vendor Name: Vendor A, Vendor B, Vendor C**: The attribute 'Vendor Name: Vendor A, Vendor B, Vendor C' specifies the possible names of the vendors that can be selected, limited to Vendor A, Vendor B, or Vendor C.
- **Contract Amount: integer between 1000 and 1000000**: The attribute 'Contract Amount: integer between 1000 and 1000000' indicates the monetary value of the contract, which must be an integer value between 1000 and 1000000.
- **KPI Score: float between 0.0 and 10.0**: The attribute 'KPI Score: float between 0.0 and 10.0' measures the vendor's performance using a floating-point score ranging from 0.0 to 10.0.
- **Compliance Status: Compliant, Non-Compliant**: The attribute 'Compliance Status: Compliant, Non-Compliant' denotes whether the vendor meets compliance standards, with possible values of Compliant or Non-Compliant.
- **Review Outcome: Satisfactory, Unsatisfactory**: The attribute 'Review Outcome: Satisfactory, Unsatisfactory' represents the result of the review, which can be either Satisfactory or Unsatisfactory.
- **Payment Status: Pending, Completed**: The attribute 'Payment Status: Pending, Completed' indicates the current state of the payment, which can be Pending or Completed.

## Binds
- **bind Select Vendor: Vendor ID, Vendor Name**: The bind 'Select Vendor: Vendor ID, Vendor Name' specifies that the activity 'Select Vendor' requires the attributes 'Vendor ID' and 'Vendor Name'.
- **bind Negotiate Contract: Vendor ID, Contract Amount**: The bind 'Negotiate Contract: Vendor ID, Contract Amount' links the 'Negotiate Contract' activity with the attributes 'Vendor ID' and 'Contract Amount'.
- **bind Monitor Performance: Vendor ID, KPI Score**: The bind 'Monitor Performance: Vendor ID, KPI Score' associates the activity 'Monitor Performance' with the attributes 'Vendor ID' and 'KPI Score'.
- **bind Review Compliance: Vendor ID, Compliance Status**: The bind 'Review Compliance: Vendor ID, Compliance Status' connects the 'Review Compliance' activity to the attributes 'Vendor ID' and 'Compliance Status'.
- **bind Issue Payment: Vendor ID, Payment Status**: The bind 'Issue Payment: Vendor ID, Payment Status' specifies that the activity 'Issue Payment' uses the attributes 'Vendor ID' and 'Payment Status'.
- **bind Conduct Review: Vendor ID, Review Outcome**: The bind 'Conduct Review: Vendor ID, Review Outcome' links the 'Conduct Review' activity with the attributes 'Vendor ID' and 'Review Outcome'.

## Interleaved Description
The MP-Declare process model for the vendor management process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Identify Needs,' which represents the initial phase where the organization determines its requirements for goods or services. This activity must be the first to occur in the process.
#### **End Constraints**
The process concludes with the activity 'Conduct Review,' which includes performing a final review of the vendor's overall performance and outcomes with the 'Review Outcome' attribute. This activity must be the last to occur in the process.

### **Frequency Constraints**

#### **Absence Constraint**
In contrast to the expected sequence of vendor-related activities, the 'Select Vendor' activity must not occur in the process at all. This exclusion reinforces process integrity by specifying that vendor selection is not permissible within this model, thereby preventing any deviation from the prescribed compliance-focused flow.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
1. The activity 'Select Vendor' is permitted to occur only if an 'Identify Needs' activity has occurred before it within the same process instance. This background establishes the foundational context that needs identification must precede any vendor-related steps.
2. The activity 'Negotiate Contract' is permitted to occur only if a 'Select Vendor' activity has occurred before it within the same process instance. This background sets up the logical sequence where vendor selection provides the necessary precursor for contract negotiations.
3. The activity 'Review Compliance' is permitted to occur only if a 'Monitor Performance' activity has occurred before it within the same process instance. This background ensures that performance monitoring must precede compliance evaluation.
4. The activity 'Issue Payment' is permitted to occur only if a 'Review Compliance' activity has occurred before it within the same process instance. This background guides the sequence so that compliance review logically precedes any payment release.

#### **Response Constraints**
1. If the 'Negotiate Contract' activity occurs (binding 'Vendor ID' and 'Contract Amount'), then the 'Sign Contract' activity must occur next. This sequence defines an ordered flow where negotiation directly leads into formalization of the agreement.
2. If the 'Sign Contract' activity occurs, then the 'Monitor Performance' activity must occur next. This sequence ensures a cohesive temporal structure in which contract signing immediately transitions into ongoing vendor assessment.
3. If the 'Issue Payment' activity occurs (binding 'Vendor ID' and 'Payment Status'), then the 'Conduct Review' activity must occur next. This sequence maintains process momentum by ensuring payment triggers the final evaluation step.

### **Immediate Ordering Constraints**

#### **Chain Response Constraints**
1. Whenever a 'Negotiate Contract' activity occurs (with attributes 'Vendor ID' and 'Contract Amount'), it must be immediately followed by a 'Sign Contract' activity in the next event position, with no other events in between. This cause-and-effect relationship captures the direct succession, ensuring an uninterrupted transition from negotiation to signing that must happen between 0 and 7 days, while allowing 'Sign Contract' events elsewhere but not between paired activities.
2. Whenever a 'Sign Contract' activity occurs, it must be immediately followed by a 'Monitor Performance' activity in the next event position, with no other events in between. This cause-and-effect relationship establishes that contract formalization directly causes the start of performance tracking, which must occur between 0 and 2 days, with multiple such pairs possible but no intervening events permitted between each matched pair.
3. Whenever an 'Issue Payment' activity occurs (binding 'Vendor ID' and 'Payment Status'), it must be immediately followed by a 'Conduct Review' activity in the next event position, with no other events in between. This cause-and-effect relationship enforces that payment release directly leads to final review, occurring between 0 and 2 days, while permitting 'Conduct Review' elsewhere but strictly prohibiting any events between each 'Issue Payment' and its corresponding 'Conduct Review'.
