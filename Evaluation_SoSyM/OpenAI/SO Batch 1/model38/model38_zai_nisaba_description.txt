#MP-Declare Model
## Activities
- **Collect Data**: The 'Collect Data' activity represents the process of gathering and accumulating data points required for subsequent analysis and report generation.
- **Analyze Data**: The 'Analyze Data' activity involves examining and interpreting the collected data to derive meaningful insights and assess report accuracy.
- **Draft Report**: The 'Draft Report' activity entails creating an initial version of the report based on the analyzed data.
- **Review Report**: The 'Review Report' activity consists of evaluating the drafted report to ensure its quality, accuracy, and completeness before approval.
- **Approve Report**: The 'Approve Report' activity represents the formal authorization of the reviewed report, marking it as ready for publication based on its approval status.
- **Publish Report**: The 'Publish Report' activity involves releasing the approved report to its intended audience or distribution channel.
- **Gather Feedback**: The 'Gather Feedback' activity includes collecting feedback from stakeholders regarding the published report, categorized by feedback type.
- **Revise Report**: The 'Revise Report' activity entails making modifications and corrections to the report based on received feedback, tracked by the revision count.

## Attributes
- **Data Points: integer between 100 and 10000**: The attribute 'Data Points: integer between 100 and 10000' represents the number of data points collected during the 'Collect Data' activity, ranging from a minimum of 100 to a maximum of 10000.
- **Report Accuracy: float between 0.0 and 100.0**: The attribute 'Report Accuracy: float between 0.0 and 100.0' represents the accuracy percentage of the data analysis, ranging from 0.0 to 100.0.
- **Approval Status: Pending, Approved, Rejected**: The attribute 'Approval Status: Pending, Approved, Rejected' specifies the possible approval states of the report, which can be 'Pending', 'Approved', or 'Rejected'.
- **Feedback Type: Positive, Negative, Neutral**: The attribute 'Feedback Type: Positive, Negative, Neutral' specifies the category of feedback received, which can be 'Positive', 'Negative', or 'Neutral'.
- **Revision Count: integer between 0 and 10**: The attribute 'Revision Count: integer between 0 and 10' represents the number of revisions made to the report, ranging from 0 to a maximum of 10.

## Binds
- **Collect Data: Data Points**: The bind 'Collect Data: Data Points' links the 'Collect Data' activity with the attribute 'Data Points', specifying that data collection involves tracking the number of data points gathered.
- **Analyze Data: Report Accuracy**: The bind 'Analyze Data: Report Accuracy' links the 'Analyze Data' activity with the attribute 'Report Accuracy', specifying that data analysis involves assessing the accuracy of the report.
- **Approve Report: Approval Status**: The bind 'Approve Report: Approval Status' links the 'Approve Report' activity with the attribute 'Approval Status', specifying that the approval process records the status of the report as Pending, Approved, or Rejected.
- **Gather Feedback: Feedback Type**: The bind 'Gather Feedback: Feedback Type' links the 'Gather Feedback' activity with the attribute 'Feedback Type', specifying that feedback collection categorizes responses as Positive, Negative, or Neutral.
- **Revise Report: Revision Count**: The bind 'Revise Report: Revision Count' links the 'Revise Report' activity with the attribute 'Revision Count', specifying that each revision of the report is tracked by a count ranging from 0 to 10.

## Interleaved Description
The MP-Declare process model for the report generation and revision process is described as follows:

### **Trace-Related Constraints**

#### **Init Constraints**
The process begins with the activity 'Collect Data,' which involves gathering and accumulating data points required for subsequent analysis and report generation. This activity tracks the 'Data Points' attribute, recording the number of data points collected, which ranges from a minimum of 100 to a maximum of 10,000. This initial activity establishes the foundational context for the entire process, ensuring that data collection serves as the starting point for all downstream activities.

### **Frequency Constraints**

#### **Existence Constraint**
The 'Publish Report' activity must occur at least once in the process. This ensures that the approved report is released to its intended audience or distribution channel, adding depth and completeness to the process by guaranteeing that the report generation effort culminates in publication.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
1. The 'Review Report' activity is permitted to occur only if an 'Approve Report' activity has occurred before it within the same process instance. This establishes a background context where the formal authorization of the report must precede its evaluation, ensuring that reviews are conducted on reports that have already undergone an approval process.
2. The 'Analyze Data' activity is permitted to occur only if an 'Approve Report' activity has occurred before it within the same process instance, provided that the activation condition is met where the 'Report Accuracy' is greater than or equal to 90. This ensures that data analysis is only performed when a prior approval exists and the analysis meets a high accuracy threshold, guaranteeing that subsequent analysis builds upon a validated foundation.

#### **Response Constraints**
1. If an 'Approve Report' activity occurs with the activation condition that the 'Approval Status' is 'Approved,' then a 'Publish Report' activity must eventually occur after the 'Approve Report' event at some point in the same process instance, within a time frame between 0 and 2 days. This defines an ordered flow where approval directly leads to publication, ensuring a cohesive temporal structure in the model. Multiple 'Approve Report' events can be pending at the same time, and a single 'Publish Report' can fulfill the obligation for all preceding 'Approve Report' events.
2. If a 'Gather Feedback' activity occurs with the activation condition that the 'Feedback Type' is 'Negative,' then a 'Revise Report' activity must eventually occur after the 'Gather Feedback' event at some point in the same process instance, within a time frame between 0 and 5 days. This establishes an ordered flow where negative feedback triggers a revision, ensuring that critical stakeholder concerns are addressed in a timely manner. Multiple 'Gather Feedback' events can be pending at the same time, and a single 'Revise Report' can fulfill the obligation for all preceding 'Gather Feedback' events.

### **Alternate Ordering Constraints**

#### **Alternate Succession Constraint**
Each occurrence of an 'Analyze Data' activity must eventually be followed by a 'Draft Report' activity, and each occurrence of a 'Draft Report' must be preceded by an 'Analyze Data,' with no intermediate occurrences of 'Analyze Data' or 'Draft Report' between them, within a time frame between 0 and 48 hours. This enforces an ordered structure with unique activity pairings, ensuring that each analysis is directly paired with a corresponding draft and that neither occurs without the other, without intervening occurrences. This condition-consequence relationship enhances process coherence by maintaining a strict one-to-one correspondence between data analysis and report drafting.

### **Negative Flexible Ordering Constraints**

#### **Not Succession Constraint**
A 'Revise Report' activity with the activation condition that the 'Revision Count' is greater than 3 and another 'Revise Report' activity must not occur such that the first 'Revise Report' event is followed by the second 'Revise Report' event at any point later in the same process instance. Similarly, a 'Revise Report' event must not be preceded by another 'Revise Report' event. This restriction ensures that once a 'Revise Report' event occurs with a 'Revision Count' greater than 3, another 'Revise Report' cannot occur afterward, and if a 'Revise Report' event occurs, it cannot have been preceded by another 'Revise Report' event with a 'Revision Count' greater than 3. Both events can occur in the same process instance, but not in the prohibited sequence. This contrast preserves the model's defined flow by preventing excessive sequential revisions beyond a critical threshold, thereby maintaining process integrity.

### **Immediate Ordering Constraints**

#### **Chain Response Constraint**
Whenever an 'Approve Report' activity occurs with the activation condition that the 'Approval Status' is 'Approved,' it must be immediately followed by a 'Publish Report' activity in the next event position, with no other events in between, within a time frame between 0 and 3 days. This immediate succession captures a direct cause-and-effect relationship where each approved report is directly and uninterruptedly followed by its publication. Multiple 'Approve Report'-'Publish Report' pairs can exist in a process instance, each adhering to this immediate succession rule. Events of 'Publish Report' can occur elsewhere in the process but not between an 'Approve Report' and its corresponding 'Publish Report.'

#### **Chain Succession Constraint**
Whenever a 'Draft Report' activity occurs, it must be immediately followed by a 'Review Report' activity, with no other events in between, within a time frame between 0 and 1 hour. Conversely, whenever a 'Review Report' event occurs, it must be immediately preceded by a 'Draft Report' event, with no other events in between. This tightly coupled sequence enforces a strict one-to-one and immediate pairing of 'Draft Report' and 'Review Report,' establishing a direct cause-and-effect relationship that ensures neither occurs without the other and that they occur consecutively without interruption. This causal link guarantees that every drafted report is immediately reviewed, maintaining the quality and accuracy of the report generation process.
