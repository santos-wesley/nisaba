#MP-Declare Model
## Activities
- **Monitor Store Entrance**: The 'Monitor Store Entrance' activity involves overseeing and observing the entry points of the store to ensure security.
- **Inspect Security Cameras**: The 'Inspect Security Cameras' activity includes checking and examining the security camera systems for proper functioning.
- **Conduct Bag Check**: The 'Conduct Bag Check' activity involves inspecting customers' bags for prohibited items or suspicious content.
- **Alert Security Personnel**: The 'Alert Security Personnel' activity includes notifying security staff about potential security threats or incidents.
- **Review Security Footage**: The 'Review Security Footage' activity involves analyzing recorded video from security cameras to identify incidents.
- **Report Incident**: The 'Report Incident' activity includes documenting and reporting any security incidents that occur in the store.
- **Escort Suspect**: The 'Escort Suspect' activity involves accompanying a suspected individual out of the premises or to a secure area.
- **Verify Alarm Trigger**: The 'Verify Alarm Trigger' activity includes confirming whether an alarm activation is genuine or a false alarm.
- **Perform Security Audit**: The 'Perform Security Audit' activity involves conducting a comprehensive evaluation of the store's security measures.
- **Update Security Protocols**: The 'Update Security Protocols' activity includes revising and improving security procedures based on audit findings.
- **Train Security Staff**: The 'Train Security Staff' activity involves providing training sessions to security personnel on procedures and protocols.
- **Handle Customer Complaint**: The 'Handle Customer Complaint' activity includes addressing and resolving complaints raised by customers.
- **Check Inventory Discrepancies**: The 'Check Inventory Discrepancies' activity involves investigating differences between recorded and actual inventory levels.
- **Conduct Emergency Drill**: The 'Conduct Emergency Drill' activity includes performing practice exercises for emergency situations.
- **Deactivate Alarm**: The 'Deactivate Alarm' activity involves turning off an alarm system after it has been triggered and verified.

## Attributes
- **Camera ID: integer between 1 and 1000**: The attribute 'Camera ID: integer between 1 and 1000' represents the unique identification number assigned to each security camera in the system.
- **Incident Severity: float between 0.1 and 10.0**: The attribute 'Incident Severity: float between 0.1 and 10.0' represents the severity level of a reported security incident.
- **Alarm Status: Active, Inactive, Triggered**: The attribute 'Alarm Status: Active, Inactive, Triggered' specifies the current state of an alarm system.
- **Security Level: Low, Medium, High**: The attribute 'Security Level: Low, Medium, High' defines the clearance or authorization level of security personnel.
- **Personnel ID: integer between 1 and 500**: The attribute 'Personnel ID: integer between 1 and 500' represents the unique identification number assigned to each security staff member.
- **Incident Type: Theft, Vandalism, Assault**: The attribute 'Incident Type: Theft, Vandalism, Assault' specifies the category of a reported security incident.
- **Customer ID: integer between 1 and 10000**: The attribute 'Customer ID: integer between 1 and 10000' represents the unique identification number assigned to each customer.
- **Audit Score: float between 0.0 and 100.0**: The attribute 'Audit Score: float between 0.0 and 100.0' represents the numerical score resulting from a security audit evaluation.
- **Complaint Status: Resolved, Unresolved**: The attribute 'Complaint Status: Resolved, Unresolved' indicates whether a customer complaint has been resolved or remains open.

- **Report Incident: Incident Severity, Incident Type**: The bind 'Report Incident: Incident Severity, Incident Type' links the 'Report Incident' activity with the attributes 'Incident Severity' and 'Incident Type'.

- **Perform Security Audit: Audit Score**: The bind 'Perform Security Audit: Audit Score' links the 'Perform Security Audit' activity with the attribute 'Audit Score'.
- **Conduct Bag Check: Customer ID**: The bind 'Conduct Bag Check: Customer ID' specifies that the activity 'Conduct Bag Check' requires the attribute 'Customer ID'.

## Constraints
- **Init[Monitor Store Entrance] | |**: The 'Monitor Store Entrance' must be the first activity to occur in the process.
- **End[Deactivate Alarm] | |**: The 'Deactivate Alarm' must be the last activity to occur in the process.
- **Existence[Report Incident] | |**: The 'Report Incident' activity must occur at least once in the process.
- **Absence[Conduct Emergency Drill] | |**: The 'Conduct Emergency Drill' must not occur in the process.
- **Response[Inspect Security Cameras, Review Security Footage] | |A.Camera ID == T.Camera ID |**: If a 'Inspect Security Cameras' activity occurs, then a 'Review Security Footage' activity must eventually occur after the 'Inspect Security Cameras' event at some point in the same process instance, and the 'Camera ID' attribute of the 'Inspect Security Cameras' activity must be equal to the 'Camera ID' attribute of the 'Review Security Footage' activity. There is no requirement on how soon or what events may occur in between. Multiple 'Inspect Security Cameras' can be pending at the same time, and a single 'Review Security Footage' can fulfill the obligation for all preceding 'Inspect Security Cameras'. If 'Inspect Security Cameras' does not occur, the constraint imposes no obligation on the occurrence of 'Review Security Footage'.
- **Chain Response[Alert Security Personnel, Escort Suspect] |A.Security Level is High |A.Personnel ID == T.Personnel ID |0,5,m**: Whenever a 'Alert Security Personnel' activity occurs, it must be immediately followed by a 'Escort Suspect' activity in the next event position, with no other events in between. This immediate succession applies only when the 'Security Level' attribute of the 'Alert Security Personnel' activity is 'High'. Additionally, the 'Personnel ID' attribute of the 'Alert Security Personnel' activity must be equal to the 'Personnel ID' attribute of the 'Escort Suspect' activity. The 'Escort Suspect' activity is allowed to happen isolated. This constraint must be triggered between 0 and 5 minutes.
- **Chain Precedence[Verify Alarm Trigger, Alert Security Personnel] |A.Alarm Status is Triggered | |0,10,m**: The 'Alert Security Personnel' activity can occur only if it is immediately preceded by 'Verify Alarm Trigger' activity, with no other activities occurring in between. This immediate precedence applies only when the 'Alarm Status' attribute of the 'Verify Alarm Trigger' activity is 'Triggered'. This constraint must be triggered between 0 and 10 minutes.
- **Co-Existence[Perform Security Audit, Update Security Protocols] |A.Audit Score < 50 | |**: If 'Perform Security Audit' activity occurs, then 'Update Security Protocols' must also occur in the same process instance, and vice-versa. This mutual obligation applies only when the 'Audit Score' attribute of the 'Perform Security Audit' activity is less than 50.
- **Succession[Conduct Bag Check, Handle Customer Complaint] | |A.Customer ID == T.Customer ID |0,1,h**: A 'Conduct Bag Check' activity must be followed by a 'Handle Customer Complaint' activity at some point later in the same process instance. Conversely, a 'Handle Customer Complaint' event can occur only if a 'Conduct Bag Check' event has occurred before it within the same process instance. Additionally, the 'Customer ID' attribute of the 'Conduct Bag Check' activity must be equal to the 'Customer ID' attribute of the 'Handle Customer Complaint' activity. This bidirectional and ordered dependency ensures that 'Conduct Bag Check' impose obligations for future 'Handle Customer Complaint', and 'Handle Customer Complaint' cannot occur without prior 'Conduct Bag Check'. Multiple 'Conduct Bag Check' and 'Handle Customer Complaint' are allowed, with each 'Conduct Bag Check' eventually leading to a 'Handle Customer Complaint' and each 'Handle Customer Complaint' being justified by a preceding 'Conduct Bag Check'. This constraint must be triggered between 0 and 1 hour.
- **Not Chain Succession[Check Inventory Discrepancies, Report Incident] | |**: A 'Check Inventory Discrepancies' activity cannot be immediately followed by a 'Report Incident' activity; there must be at least one other event between them. Similarly, a 'Report Incident' event cannot be immediately preceded by a 'Check Inventory Discrepancies' event. This constraint allows multiple occurrences of 'Check Inventory Discrepancies' and 'Report Incident' in any order, provided they are not adjacent in the event sequence.
- **Exclusive Choice[Train Security Staff, Conduct Emergency Drill] | |**: Exactly one of the activities 'Train Security Staff' or 'Conduct Emergency Drill' must occur in the process instance. This means that the process is compliant if only 'Train Security Staff' event occurs without any occurrence of 'Conduct Emergency Drill' event, or only 'Conduct Emergency Drill' occurs without any occurrence of 'Train Security Staff'. The process is non-compliant if both 'Train Security Staff' and 'Conduct Emergency Drill' occur, or if neither occurs. The constraint enforces a mutual exclusivity and a mandatory occurrence of one of the specified activities.
- **Precedence[Escort Suspect, Report Incident] | |A.Incident Type is Theft |**: The 'Report Incident' activity is permitted to occur only if a 'Escort Suspect' activity has occurred before it within the same process instance, and the 'Incident Type' attribute of the 'Report Incident' activity must be 'Theft'. Multiple 'Escort Suspect' can occur, and any number of events (including other 'Report Incident') can happen between a 'Escort Suspect' and a subsequent 'Report Incident'. This ensures that certain actions cannot proceed without the necessary prerequisites being met first.
- **Not Precedence[Deactivate Alarm, Verify Alarm Trigger] | |**: A 'Verify Alarm Trigger' activity cannot be preceded by a 'Deactivate Alarm' within the same process instance. If a 'Deactivate Alarm' event has occurred at any point before a 'Verify Alarm Trigger' event, then 'Verify Alarm Trigger' is disallowed. Multiple instances of 'Verify Alarm Trigger' and 'Deactivate Alarm' can occur, but all instances of 'Verify Alarm Trigger' must occur before any instance of 'Deactivate Alarm'.
- **Not Responded Existence[Handle Customer Complaint, Conduct Bag Check] |A.Complaint Status is Resolved |A.Customer ID == T.Customer ID |**: If a 'Handle Customer Complaint' activity occurs in a process instance, then a 'Conduct Bag Check' activity must not occur anywhere in the same process instance. This applies only when the 'Complaint Status' attribute of the 'Handle Customer Complaint' activity is 'Resolved'. Additionally, the 'Customer ID' attribute of the 'Handle Customer Complaint' activity must be equal to the 'Customer ID' attribute of the 'Conduct Bag Check' activity. This means that the occurrence of 'Handle Customer Complaint' event prohibits any occurrence of 'Conduct Bag Check' event. However, if 'Handle Customer Complaint' does not occur, 'Conduct Bag Check' may occur freely. Multiple occurrences of 'Handle Customer Complaint' are allowed, provided 'Conduct Bag Check' does not occur at all in the process instance.
- **Not Succession[Review Security Footage, Inspect Security Cameras] | |**: The 'Review Security Footage' activity and 'Inspect Security Cameras' activity must not occur such that the 'Review Security Footage' event is followed by the 'Inspect Security Cameras' event at any point later in the same process instance. Similarly, an 'Inspect Security Cameras' event must not be preceded by a 'Review Security Footage' event. This means that once a 'Review Security Footage' occurs, 'Inspect Security Cameras' cannot occur afterward, and if 'Inspect Security Cameras' event occurs, it cannot have been preceded by a 'Review Security Footage' event. Both events can occur in the same process instance, but not in the prohibited sequence.


## Interleaved Description
The MP-Declare process model for the store security process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Monitor Store Entrance,' which involves overseeing and observing the entry points of the store to ensure security. This establishes the initial context for all subsequent security activities.
#### **End Constraints**
The process concludes with the activity 'Deactivate Alarm,' which involves turning off an alarm system after it has been triggered and verified. This activity must be the last to occur in the process, providing a definitive closure to the security workflow.

### **Frequency Constraints**
#### **Existence Constraint**
The 'Report Incident' activity must occur at least once in the process. This ensures that any security incidents are documented and reported, adding depth and accountability to the process.
#### **Absence Constraint**
In contrast, the 'Conduct Emergency Drill' activity must not occur in the process. This exclusion reinforces process integrity by specifying that emergency drills are not part of this particular security workflow.
#### **Exclusive Choice Constraint**
Exactly one of the activities 'Train Security Staff' or 'Conduct Emergency Drill' must occur in the process instance. Since 'Conduct Emergency Drill' is already excluded by the Absence constraint, this effectively mandates that 'Train Security Staff' must occur, providing a summary of the required training activity.

### **Flexible Ordering Constraints**
#### **Precedence Constraints**
The 'Report Incident' activity is permitted to occur only if an 'Escort Suspect' activity has occurred before it, with the condition that the 'Incident Type' attribute of the 'Report Incident' activity is 'Theft'. This sets up an initial context where a suspect must be escorted before reporting a theft incident, ensuring that the necessary prerequisite is met.
#### **Response Constraints**
If an 'Inspect Security Cameras' activity occurs, then a 'Review Security Footage' activity must eventually occur after it, with the condition that the 'Camera ID' attribute of the 'Inspect Security Cameras' activity equals the 'Camera ID' attribute of the 'Review Security Footage' activity. This defines an ordered flow where camera inspection leads to footage review, ensuring a cohesive temporal structure.
#### **Succession Constraints**
A 'Conduct Bag Check' activity must be followed by a 'Handle Customer Complaint' activity at some point later, and conversely, a 'Handle Customer Complaint' event can occur only if a 'Conduct Bag Check' event has occurred before it, with the condition that the 'Customer ID' attributes match. This establishes a causal link, ensuring each bag check logically leads to a customer complaint handling, creating a cohesive progression within the process.

### **Exclusivity Constraints**
#### **Not Responded Existence Constraint**
If a 'Handle Customer Complaint' activity occurs with the condition 'Complaint Status is Resolved', then a 'Conduct Bag Check' activity must not occur anywhere in the same process instance, with the condition that the 'Customer ID' attributes match. This contrast prevents a resolved complaint from being followed by a bag check for the same customer, refining the model by disallowing specific contingent occurrences.
#### **Not Succession Constraint**
The 'Review Security Footage' activity and 'Inspect Security Cameras' activity must not occur such that the 'Review Security Footage' event is followed by the 'Inspect Security Cameras' event at any point later. This contrast restricts overlapping sequences, ensuring that footage review does not precede camera inspection, preserving the model's defined flow.

### **Negative Flexible Ordering Constraints**
#### **Not Precedence Constraint**
A 'Verify Alarm Trigger' activity cannot be preceded by a 'Deactivate Alarm' within the same process instance. This contrast restricts activities from occurring in a specific order, ensuring that alarm verification occurs before any deactivation, preserving the intended sequence.
#### **Not Chain Succession Constraint**
A 'Check Inventory Discrepancies' activity cannot be immediately followed by a 'Report Incident' activity, and vice versa. This contrast prevents direct succession, ensuring that these activities are not adjacent in the event sequence, thereby refining the process model by excluding specific immediate sequences.

### **Immediate Ordering Constraints**
#### **Chain Precedence Constraint**
The 'Alert Security Personnel' activity can occur only if it is immediately preceded by a 'Verify Alarm Trigger' activity, with the condition that the 'Alarm Status' attribute of the 'Verify Alarm Trigger' activity is 'Triggered'. This sequence establishes an immediate dependency, ensuring that alerting security follows directly from a triggered alarm verification, with no intervening events.
#### **Chain Response Constraint**
Whenever an 'Alert Security Personnel' activity occurs with the condition 'Security Level is High', it must be immediately followed by an 'Escort Suspect' activity, with the condition that the 'Personnel ID' attributes match. This cause-effect relationship captures immediate succession, ensuring a direct and immediate response to high-level security alerts.

### **Mutual Dependency Constraints**
#### **Co-Existence Constraint**
If a 'Perform Security Audit' activity occurs with the condition 'Audit Score < 50', then 'Update Security Protocols' must also occur in the same process instance, and vice versa. This conjunction establishes a mutual dependency, ensuring that both activities occur together when the audit score is low, maintaining process integrity.
