#MP-Declare Model
## Activities
- **Monitor Store Entrance**: The 'Monitor Store Entrance' activity involves observing and surveilling the entrance area of the store to ensure security and detect any suspicious activity.
- **Inspect Security Cameras**: The 'Inspect Security Cameras' activity entails reviewing and examining the security camera feeds to monitor ongoing activities within the store.
- **Conduct Bag Check**: The 'Conduct Bag Check' activity involves checking the bags of customers or visitors to prevent unauthorized items from entering or leaving the store.
- **Alert Security Personnel**: The 'Alert Security Personnel' activity consists of notifying security staff about a potential security threat or incident requiring immediate attention.
- **Review Security Footage**: The 'Review Security Footage' activity involves analyzing previously recorded security camera footage to investigate incidents or verify events.
- **Report Incident**: The 'Report Incident' activity entails documenting and formally reporting a security incident, including its severity and type, for record-keeping and follow-up.
- **Escort Suspect**: The 'Escort Suspect' activity involves accompanying a suspected individual within or out of the store premises while maintaining security protocols.
- **Verify Alarm Trigger**: The 'Verify Alarm Trigger' activity consists of confirming whether an alarm activation is genuine or a false alarm by inspecting the relevant alarm status.
- **Perform Security Audit**: The 'Perform Security Audit' activity entails conducting a comprehensive assessment of the store's security measures and assigning an audit score based on the findings.
- **Update Security Protocols**: The 'Update Security Protocols' activity involves revising and improving the existing security procedures and guidelines to enhance store safety.
- **Train Security Staff**: The 'Train Security Staff' activity consists of providing training sessions to security personnel to ensure they are equipped with the necessary skills and knowledge.
- **Handle Customer Complaint**: The 'Handle Customer Complaint' activity involves receiving, processing, and resolving complaints raised by customers regarding their experience or security-related issues.
- **Check Inventory Discrepancies**: The 'Check Inventory Discrepancies' activity entails investigating mismatches or inconsistencies in the store's inventory records to identify potential theft or errors.
- **Conduct Emergency Drill**: The 'Conduct Emergency Drill' activity involves organizing and executing a simulated emergency scenario to prepare staff for real emergency situations.
- **Deactivate Alarm**: The 'Deactivate Alarm' activity consists of turning off an active alarm system once the situation has been assessed and resolved.

## Attributes
- **Camera ID: integer between 1 and 1000**: The attribute 'Camera ID: integer between 1 and 1000' represents the unique identification number assigned to each security camera within the store.
- **Incident Severity: float between 0.1 and 10.0**: The attribute 'Incident Severity: float between 0.1 and 10.0' represents the severity level of a reported security incident on a floating-point scale.
- **Alarm Status: Active, Inactive, Triggered**: The attribute 'Alarm Status: Active, Inactive, Triggered' specifies the possible states of the alarm system, indicating whether it is active, inactive, or currently triggered.
- **Security Level: Low, Medium, High**: The attribute 'Security Level: Low, Medium, High' indicates the security clearance level assigned to security personnel.
- **Personnel ID: integer between 1 and 500**: The attribute 'Personnel ID: integer between 1 and 500' represents the unique identification number assigned to each security personnel member.
- **Incident Type: Theft, Vandalism, Assault**: The attribute 'Incident Type: Theft, Vandalism, Assault' specifies the category of a security incident, indicating whether it involves theft, vandalism, or assault.
- **Customer ID: integer between 1 and 10000**: The attribute 'Customer ID: integer between 1 and 10000' represents the unique identification number assigned to each customer within the store system.
- **Audit Score: float between 0.0 and 100.0**: The attribute 'Audit Score: float between 0.0 and 100.0' represents the score achieved during a security audit, reflecting the overall effectiveness of the store's security measures.
- **Complaint Status: Resolved, Unresolved**: The attribute 'Complaint Status: Resolved, Unresolved' specifies the current resolution state of a customer complaint, indicating whether it has been resolved or remains unresolved.

## Binds
- **Inspect Security Cameras: Camera ID**: The bind 'Inspect Security Cameras: Camera ID' links the 'Inspect Security Cameras' activity with the attribute 'Camera ID', specifying that the camera inspection requires the identification of the camera being inspected.
- **Report Incident: Incident Severity, Incident Type**: The bind 'Report Incident: Incident Severity, Incident Type' links the 'Report Incident' activity with the attributes 'Incident Severity' and 'Incident Type', specifying that reporting an incident requires recording its severity level and type.
- **Verify Alarm Trigger: Alarm Status**: The bind 'Verify Alarm Trigger: Alarm Status' links the 'Verify Alarm Trigger' activity with the attribute 'Alarm Status', specifying that verifying an alarm trigger requires checking the current status of the alarm.
- **Alert Security Personnel: Personnel ID, Security Level**: The bind 'Alert Security Personnel: Personnel ID, Security Level' links the 'Alert Security Personnel' activity with the attributes 'Personnel ID' and 'Security Level', specifying that alerting security personnel requires identifying the personnel and their security clearance level.
- **Handle Customer Complaint: Customer ID, Complaint Status**: The bind 'Handle Customer Complaint: Customer ID, Complaint Status' links the 'Handle Customer Complaint' activity with the attributes 'Customer ID' and 'Complaint Status', specifying that handling a complaint requires identifying the customer and tracking the resolution status of the complaint.
- **Perform Security Audit: Audit Score**: The bind 'Perform Security Audit: Audit Score' links the 'Perform Security Audit' activity with the attribute 'Audit Score', specifying that performing a security audit requires recording the resulting audit score.
- **Conduct Bag Check: Customer ID**: The bind 'Conduct Bag Check: Customer ID' links the 'Conduct Bag Check' activity with the attribute 'Customer ID', specifying that conducting a bag check requires identifying the customer whose bag is being checked.

## Interleaved Description
The MP-Declare process model for the store security process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Monitor Store Entrance,' which involves observing and surveilling the entrance area of the store to ensure security and detect any suspicious activity. This activity must be the first to occur in the process, establishing the initial context for all subsequent security operations.

#### **End Constraints**
The process concludes with the activity 'Deactivate Alarm,' which consists of turning off an active alarm system once the situation has been assessed and resolved. This activity must be the last to occur in the process, ensuring that all security matters are fully addressed before the alarm system is deactivated and the process is formally closed.

### **Frequency Constraints**

#### **Existence Constraint**
The 'Report Incident' activity must occur at least once in the process. This activity entails documenting and formally reporting a security incident, including its severity level (on a scale from 0.1 to 10.0) and type (Theft, Vandalism, or Assault), for record-keeping and follow-up. This requirement adds depth and reliability to the process by ensuring that all security incidents are properly documented.

#### **Absence Constraint**
The 'Conduct Emergency Drill' activity must not occur in the process. While this activity would normally involve organizing and executing a simulated emergency scenario to prepare staff for real emergency situations, its exclusion highlights the focus on real-time security operations rather than preparatory exercises, reinforcing the process's operational integrity.

#### **Exclusive Choice Constraint**
Exactly one of the activities 'Train Security Staff' or 'Conduct Emergency Drill' must occur in the process instance. However, since the 'Conduct Emergency Drill' activity is already prohibited by the Absence constraint, the process effectively mandates the occurrence of 'Train Security Staff,' which consists of providing training sessions to security personnel to ensure they are equipped with the necessary skills and knowledge. This mutual exclusivity and mandatory occurrence ensure precision within the process model by setting fixed boundaries on which preparatory activity is permissible.

### **Flexible Ordering Constraints**

#### **Precedence Constraint**
The 'Report Incident' activity is permitted to occur only if an 'Escort Suspect' activity has occurred before it within the same process instance, provided that the 'Incident Type' attribute of the 'Report Incident' event is 'Theft.' This means that when reporting a theft incident, the suspect must have been escorted within or out of the store premises while maintaining security protocols prior to the formal report. Multiple 'Escort Suspect' events can occur, and any number of events can happen between an 'Escort Suspect' and a subsequent 'Report Incident,' setting up a logical sequence that guides the process flow for theft-related incidents.

#### **Response Constraint**
If an 'Inspect Security Cameras' activity occurs, then a 'Review Security Footage' activity must eventually occur after it at some point in the same process instance, provided that the 'Camera ID' attribute (an integer between 1 and 1000) of the 'Inspect Security Cameras' event matches the 'Camera ID' attribute of the 'Review Security Footage' event. This ordered flow ensures that whenever a security camera is inspected, the previously recorded footage from that same camera is subsequently analyzed to investigate incidents or verify events. There is no requirement on how soon the review must follow or what events may occur in between, and multiple 'Inspect Security Cameras' events can be pending simultaneously, with a single 'Review Security Footage' event fulfilling the obligation for all preceding inspections.

#### **Succession Constraint**
A 'Conduct Bag Check' activity must be followed by a 'Handle Customer Complaint' activity at some point later in the same process instance, provided that the 'Customer ID' attribute (an integer between 1 and 10000) of the 'Conduct Bag Check' event matches the 'Customer ID' attribute of the 'Handle Customer Complaint' event. Conversely, a 'Handle Customer Complaint' event can occur only if a 'Conduct Bag Check' event has occurred before it. This bidirectional and ordered dependency must be satisfied within 0 to 1 hour, establishing a causal link where each bag check eventually leads to a customer complaint being received, processed, and resolved, and each complaint is justified by a preceding bag check for the same customer.

### **Immediate Ordering Constraints**

#### **Chain Precedence Constraint**
The 'Alert Security Personnel' activity can occur only if it is immediately preceded by a 'Verify Alarm Trigger' activity, with no other activities occurring in between. This constraint applies when the activation condition specifies that the 'Alarm Status' is 'Triggered.' The time condition requires that the 'Alert Security Personnel' activity must occur within 0 to 10 minutes after the preceding 'Verify Alarm Trigger' event, where the alarm status is confirmed as genuine or a false alarm. This immediate dependency ensures that security personnel are only alerted immediately after an alarm trigger is verified, making the sequence explicit and precise. Multiple 'Verify Alarm Trigger'-'Alert Security Personnel' pairs can exist within the process, each adhering to this immediate precedence rule.

#### **Chain Response Constraint**
Whenever an 'Alert Security Personnel' activity occurs with the activation condition that the 'Security Level' is 'High,' it must be immediately followed by an 'Escort Suspect' activity in the next event position, with no other events in between. Additionally, the 'Personnel ID' attribute (an integer between 1 and 500) of the 'Alert Security Personnel' event must match the 'Personnel ID' attribute of the 'Escort Suspect' event. This immediate succession must occur within 0 to 5 minutes, capturing a direct cause-and-effect relationship where each high-security-level alert immediately results in the suspect being escorted. Multiple 'Alert Security Personnel'-'Escort Suspect' pairs can exist in a process instance, each adhering to this immediate succession rule. The 'Escort Suspect' activity is allowed to happen elsewhere in the process but not between an 'Alert Security Personnel' event and its corresponding 'Escort Suspect' event.

### **Mutual Dependency Constraints**

#### **Co-Existence Constraint**
If a 'Perform Security Audit' activity occurs with the activation condition that the 'Audit Score' is less than 50 (on a scale from 0.0 to 100.0), then an 'Update Security Protocols' activity must also occur in the same process instance, and vice versa. This mutual obligation ensures that neither event can occur without the other when the audit score is below 50, establishing a mutual dependency where a poor security audit result invariably triggers a revision and improvement of the existing security procedures and guidelines. The events can occur multiple times and in any order relative to each other. If neither event occurs, the constraint is still considered satisfied.

### **Negative Dependency Constraints**

#### **Not Responded Existence Constraint**
If a 'Handle Customer Complaint' activity occurs with the activation condition that the 'Complaint Status' is 'Resolved,' then a 'Conduct Bag Check' activity must not occur anywhere in the same process instance, provided that the 'Customer ID' attribute of the 'Handle Customer Complaint' event matches the 'Customer ID' attribute of the 'Conduct Bag Check' event. This means that once a customer's complaint has been resolved, no further bag checks can be conducted for that same customer within the process instance. This prevents certain dependencies by ensuring that resolved complaints prohibit subsequent bag checks for the same customer, thereby refining the model. However, if 'Handle Customer Complaint' does not occur with a resolved status, 'Conduct Bag Check' may occur freely. Multiple occurrences of 'Handle Customer Complaint' with resolved status are allowed, provided 'Conduct Bag Check' does not occur at all for the same customer.

### **Negative Flexible Ordering Constraints**

#### **Not Precedence Constraint**
A 'Verify Alarm Trigger' activity cannot be preceded by a 'Deactivate Alarm' activity within the same process instance. This means that if any 'Deactivate Alarm' event has occurred before a 'Verify Alarm Trigger' event, then 'Verify Alarm Trigger' is disallowed. This restriction ensures that the alarm system cannot be verified after it has been deactivated, preserving the intended sequence where all alarm verifications must occur before any deactivation. Multiple instances of 'Verify Alarm Trigger' and 'Deactivate Alarm' can occur, but all instances of 'Verify Alarm Trigger' must occur before any instance of 'Deactivate Alarm.'

#### **Not Succession Constraint**
A 'Review Security Footage' activity and an 'Inspect Security Cameras' activity must not occur such that the 'Review Security Footage' event is followed by the 'Inspect Security Cameras' event at any point later in the same process instance. Similarly, an 'Inspect Security Cameras' event must not be preceded by a 'Review Security Footage' event. This means that once a 'Review Security Footage' occurs, 'Inspect Security Cameras' cannot occur afterward, and if an 'Inspect Security Cameras' event occurs, it cannot have been preceded by a 'Review Security Footage' event. Both events can occur in the same process instance, but not in the prohibited sequence, thereby preserving the model's defined flow where camera inspections always precede footage reviews and never the reverse.

### **Negative Immediate Ordering Constraints**

#### **Not Chain Succession Constraint**
A 'Check Inventory Discrepancies' activity cannot be immediately followed by a 'Report Incident' activity; there must be at least one other event between them. Similarly, a 'Report Incident' event cannot be immediately preceded by a 'Check Inventory Discrepancies' event. This constraint prevents direct succession between the investigation of inventory mismatches or inconsistencies and the formal reporting of a security incident, ensuring that inventory discrepancies are not impulsively linked to incident reports without intervening assessment or verification steps. Multiple occurrences of 'Check Inventory Discrepancies' and 'Report Incident' are allowed in any order, provided they are not adjacent in the event sequence.
