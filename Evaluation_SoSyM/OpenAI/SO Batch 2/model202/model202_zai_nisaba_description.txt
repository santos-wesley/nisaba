#MP-Declare Model
## Activities
- **Receive Currency**: The 'Receive Currency' activity represents the initial step of accepting currency from a customer for an exchange transaction.
- **Verify Currency Authenticity**: The 'Verify Currency Authenticity' activity involves checking the genuineness of the received currency to prevent fraud.
- **Calculate Exchange Rate**: The 'Calculate Exchange Rate' activity determines the applicable exchange rate for converting the received currency.
- **Approve Exchange**: The 'Approve Exchange' activity authorizes the currency exchange transaction after verification and rate calculation.
- **Reject Exchange**: The 'Reject Exchange' activity declines the currency exchange transaction when conditions are not met.
- **Process Exchange**: The 'Process Exchange' activity executes the approved currency exchange transaction.
- **Issue Receipt**: The 'Issue Receipt' activity generates a receipt for the completed currency exchange transaction.
- **Notify Customer**: The 'Notify Customer' activity informs the customer about the status or outcome of the exchange transaction.
- **Record Transaction**: The 'Record Transaction' activity logs the details of the completed exchange transaction for record-keeping purposes.
- **Update Exchange Rates**: The 'Update Exchange Rates' activity refreshes the current exchange rates used for currency conversion.

## Attributes
- **Amount: integer between 1 and 10000**: The attribute 'Amount: integer between 1 and 10000' represents the quantity of currency received for exchange, ranging from 1 to 10000.
- **Exchange Rate: float between 0.5 and 1.5**: The attribute 'Exchange Rate: float between 0.5 and 1.5' specifies the conversion rate applied during the currency exchange, ranging from 0.5 to 1.5.
- **Currency Type: USD, EUR, GBP, JPY**: The attribute 'Currency Type: USD, EUR, GBP, JPY' defines the types of currencies accepted for exchange, including US Dollar, Euro, British Pound, and Japanese Yen.
- **Exchange Status: Pending, Approved, Rejected**: The attribute 'Exchange Status: Pending, Approved, Rejected' indicates the current state of the exchange transaction, which can be Pending, Approved, or Rejected.
- **Transaction ID: integer between 1000 and 9999**: The attribute 'Transaction ID: integer between 1000 and 9999' represents the unique identification number assigned to each exchange transaction, ranging from 1000 to 9999.

- **Issue Receipt: Transaction ID**: The bind 'Issue Receipt: Transaction ID' links the 'Issue Receipt' activity with the attribute 'Transaction ID'.

## Interleaved Description
The MP-Declare process model for the currency exchange transaction process is described as follows:

### **Trace-Related Constraints**

#### **Init Constraints**
The process begins with the activity 'Receive Currency,' which involves accepting currency from a customer for an exchange transaction. This activity is bound to the attributes 'Amount' (an integer between 1 and 10000) and 'Currency Type' (which can be USD, EUR, GBP, or JPY), establishing the foundational context for the entire exchange process.

#### **End Constraints**
The process concludes with the activity 'Issue Receipt,' which generates a receipt for the completed currency exchange transaction. This activity is bound to the attribute 'Transaction ID' (an integer between 1000 and 9999) and must be the last activity to occur in the process, ensuring that every exchange transaction is properly documented before the process terminates.

### **Frequency Constraints**

#### **Existence Constraint**
The 'Calculate Exchange Rate' activity must occur at least once in the process. This activity, which is bound to the 'Exchange Rate' attribute (a float between 0.5 and 1.5), determines the applicable exchange rate for converting the received currency. This requirement adds depth and reliability to the process by ensuring that the exchange rate is always established before any further processing occurs.

#### **Exactly Constraint**
The 'Approve Exchange' activity must occur exactly once in the process. This activity, bound to the 'Exchange Status' attribute, authorizes the currency exchange transaction after verification and rate calculation. This precise boundary ensures that the approval step is neither skipped nor repeated, maintaining the integrity and unambiguity of the transaction authorization.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
1. The 'Verify Currency Authenticity' activity is permitted to occur only if an 'Approve Exchange' activity has occurred before it within the same process instance. This establishes a context where the approval of the exchange serves as a prerequisite for verifying the genuineness of the received currency, guiding the logical sequence of verification and approval activities.
2. The 'Calculate Exchange Rate' activity is permitted to occur only if a 'Process Exchange' activity has occurred before it within the same process instance. This ensures that the exchange rate calculation is contextually grounded in a prior processing step, maintaining a logical flow within the model.
3. The 'Receive Currency' activity is permitted to occur only if a 'Verify Currency Authenticity' activity has occurred before it within the same process instance. This sets up an initial context where the authenticity of the currency must be verified before it is formally received, ensuring that fraudulent currency is identified early in the process.

#### **Response Constraints**
1. If an 'Approve Exchange' activity occurs with the activation condition that 'Exchange Status is Approved,' then a 'Process Exchange' activity must eventually occur after the 'Approve Exchange' event at some point within 0 to 2 hours in the same process instance. The 'Process Exchange' activity, bound to the 'Transaction ID' attribute, executes the approved currency exchange transaction. There is no requirement on how soon or what events may occur in between, and multiple 'Approve Exchange' events can be pending at the same time, with a single 'Process Exchange' fulfilling the obligation for all preceding approvals. This ensures a cohesive temporal structure where approval leads to execution.
2. If a 'Reject Exchange' activity occurs with the activation condition that 'Exchange Status is Rejected,' then a 'Notify Customer' activity must eventually occur after the 'Reject Exchange' event at some point within 0 to 1 hour in the same process instance. The 'Notify Customer' activity, bound to the 'Exchange Status' attribute, informs the customer about the status or outcome of the exchange transaction. Multiple 'Reject Exchange' events can be pending simultaneously, and a single 'Notify Customer' can fulfill the obligation for all preceding rejections. This ensures that the customer is promptly informed of any rejection, maintaining transparency in the process.
3. If a 'Process Exchange' activity occurs, then a 'Record Transaction' activity must eventually occur after the 'Process Exchange' event at some point within 0 to 1 hour in the same process instance, with the correlation condition that the 'Transaction ID' of the 'Process Exchange' event matches the 'Transaction ID' of the 'Record Transaction' event. The 'Record Transaction' activity logs the details of the completed exchange transaction for record-keeping purposes. Multiple 'Process Exchange' events can be pending at the same time, and a single 'Record Transaction' can fulfill the obligation for all preceding processing events, provided the transaction IDs match. This ensures that every processed exchange is properly logged, maintaining a complete audit trail.

### **Dependency Constraints**

#### **Responded Existence Constraint**
If the 'Process Exchange' activity occurs in a process instance, then the 'Update Exchange Rates' activity must also occur at least once within the same process instance, either before or after the 'Process Exchange' event. The 'Update Exchange Rates' activity, bound to the 'Exchange Rate' attribute, refreshes the current exchange rates used for currency conversion. If 'Process Exchange' does not occur, there is no requirement for 'Update Exchange Rates' to occur. Multiple occurrences of 'Process Exchange' are satisfied by at least one occurrence of 'Update Exchange Rates,' and multiple 'Update Exchange Rates' instances are allowed. This establishes a dependency where the execution of an exchange necessitates the presence of a rate update, enhancing coherence and ensuring that exchange rates remain current.

### **Exclusivity Constraints**

#### **Not Co-Existence Constraint**
The 'Verify Currency Authenticity' activity and the 'Approve Exchange' activity cannot both occur within the same process instance. This means that if 'Verify Currency Authenticity' occurs one or more times, 'Approve Exchange' must not occur at all in that process instance, and vice versa. It is acceptable for neither event to occur. This mutual exclusion enforces distinct process variants based on which event (if any) occurs, maintaining process integrity by preventing conflicting verification and approval activities from coexisting.

### **Negative Flexible Ordering Constraints**

#### **Not Succession Constraint**
The 'Receive Currency' activity and the 'Reject Exchange' activity must not occur such that the 'Receive Currency' event is followed by the 'Reject Exchange' event at any point later in the same process instance. Similarly, a 'Reject Exchange' event must not be preceded by a 'Receive Currency' event. This means that once a 'Receive Currency' occurs, 'Reject Exchange' cannot occur afterward, and if 'Reject Exchange' occurs, it cannot have been preceded by 'Receive Currency.' Both events can occur in the same process instance, but not in the prohibited sequence. This restriction preserves the model's defined flow by ensuring that a received currency transaction is not subsequently rejected, thereby maintaining the integrity of the exchange process.

### **Immediate Ordering Constraints**

#### **Chain Succession Constraints**
1. Whenever a 'Calculate Exchange Rate' activity occurs, it must be immediately followed by an 'Update Exchange Rates' activity, with no other events in between, within 0 to 30 minutes. Conversely, whenever an 'Update Exchange Rates' event occurs, it must be immediately preceded by a 'Calculate Exchange Rate' event, with no other events in between. This enforces a strict one-to-one and immediate pairing of 'Calculate Exchange Rate' and 'Update Exchange Rates,' ensuring that neither occurs without the other and that they occur consecutively without interruption. This tightly coupled sequence guarantees that every rate calculation is directly linked to a rate update, maintaining consistency in the exchange rate management process.
2. Whenever a 'Receive Currency' activity occurs, it must be immediately followed by a 'Record Transaction' activity, with no other events in between, within 0 to 1 day, with the correlation condition that the 'Transaction ID' of the 'Receive Currency' event matches the 'Transaction ID' of the 'Record Transaction' event. Conversely, whenever a 'Record Transaction' event occurs, it must be immediately preceded by a 'Receive Currency' event, with no other events in between. This enforces a strict one-to-one and immediate pairing of 'Receive Currency' and 'Record Transaction,' ensuring that neither occurs without the other and that they occur consecutively without interruption. This tightly coupled sequence ensures that every received currency is directly linked to a recorded transaction, providing a seamless and immediate audit trail from the moment currency is accepted.
