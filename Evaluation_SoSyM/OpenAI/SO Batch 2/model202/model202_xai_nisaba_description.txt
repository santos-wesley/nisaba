#MP-Declare Model
## Activities
- **Receive Currency**: The 'Receive Currency' activity represents the initial step where the customer submits the currency for exchange.
- **Verify Currency Authenticity**: The 'Verify Currency Authenticity' activity involves checking the submitted currency for genuineness and validity.
- **Calculate Exchange Rate**: The 'Calculate Exchange Rate' activity computes the applicable exchange rate for the currency being exchanged.
- **Approve Exchange**: The 'Approve Exchange' activity confirms and authorizes the currency exchange transaction.
- **Reject Exchange**: The 'Reject Exchange' activity denies the currency exchange request, often due to issues like inauthenticity or policy violations.
- **Process Exchange**: The 'Process Exchange' activity executes the actual exchange of currencies based on the approved rate.
- **Issue Receipt**: The 'Issue Receipt' activity generates and provides a receipt for the completed exchange transaction.
- **Notify Customer**: The 'Notify Customer' activity informs the customer about the status of their exchange request, such as approval or rejection.
- **Record Transaction**: The 'Record Transaction' activity logs the details of the exchange for accounting and auditing purposes.
- **Update Exchange Rates**: The 'Update Exchange Rates' activity refreshes the system's exchange rate data, possibly based on market changes.

## Attributes
- **Amount: integer between 1 and 10000**: The attribute 'Amount: integer between 1 and 10000' represents the quantity of currency being exchanged, constrained within the range of 1 to 10000 units.
- **Exchange Rate: float between 0.5 and 1.5**: The attribute 'Exchange Rate: float between 0.5 and 1.5' indicates the rate at which one currency is exchanged for another, with values ranging from 0.5 to 1.5.
- **Currency Type: USD, EUR, GBP, JPY**: The attribute 'Currency Type: USD, EUR, GBP, JPY' specifies the type of currency involved in the exchange, limited to USD, EUR, GBP, or JPY.
- **Exchange Status: Pending, Approved, Rejected**: The attribute 'Exchange Status: Pending, Approved, Rejected' tracks the current state of the exchange request, which can be Pending, Approved, or Rejected.
- **Transaction ID: integer between 1000 and 9999**: The attribute 'Transaction ID: integer between 1000 and 9999' is a unique identifier for each exchange transaction, ranging from 1000 to 9999.

This means that once a 'Receive Currency' occurs, 'Reject Exchange' cannot occur afterward, and if 'Reject Exchange' event occurs, it cannot have been preceded by a 'Receive Currency' event. ## Interleaved Description
The MP-Declare process model for the currency exchange process is described as follows:

### **Trace-Related Constraints**
#### **Init Constraints**
The process begins with the activity 'Receive Currency,' which represents the initial step where the customer submits the currency for exchange along with its 'Amount' and 'Currency Type' attributes. This activity must be the first to occur in the process.
#### **End Constraints**
The process concludes with the activity 'Issue Receipt,' which generates and provides a receipt for the completed exchange transaction using the 'Transaction ID' attribute. This activity must be the last to occur in the process.

### **Frequency Constraints**

#### **Existence Constraint**
The 'Calculate Exchange Rate' activity must occur at least once in the process. This ensures that the applicable exchange rate for the currency being exchanged is always computed, adding depth and reliability to every transaction.

#### **Exactly Constraint**
The 'Approve Exchange' activity must occur exactly once in the process. This sets a fixed boundary, ensuring precision by authorizing the currency exchange transaction only a single time.

#### **Not Co-Existence Constraint**
The 'Verify Currency Authenticity' activity and the 'Approve Exchange' activity cannot both occur within the same process instance. This exclusion reinforces process integrity by specifying that these two activities are mutually prohibited, thereby maintaining separation between authenticity verification and approval pathways.

### **Dependency Constraints**

#### **Responded Existence Constraint**
If the 'Process Exchange' activity occurs, then the 'Update Exchange Rates' activity must also occur at least once within the same process instance, either before or after. This establishes a dependency where executing the actual exchange of currencies based on the approved rate necessitates refreshing the system's exchange rate data.

### **Flexible Ordering Constraints**

#### **Precedence Constraints**
1. The activity 'Verify Currency Authenticity' is permitted to occur only if an 'Approve Exchange' activity has occurred before it. This sets up the initial context that approval must precede authenticity verification.
2. The activity 'Process Exchange' is permitted to occur only if a 'Calculate Exchange Rate' activity has occurred before it. This background ensures the exchange rate is computed prior to executing the currency exchange.
3. The activity 'Receive Currency' is permitted to occur only if a 'Verify Currency Authenticity' activity has occurred before it. This establishes the foundational sequence requiring authenticity checks before currency submission.

#### **Response Constraints**
1. If an 'Approve Exchange' activity occurs where the 'Exchange Status is Approved,' then a 'Process Exchange' activity must eventually occur after it within 0 to 2 hours. This defines an ordered flow from approval to actual processing, with a single 'Process Exchange' able to fulfill multiple pending approvals.
2. If a 'Reject Exchange' activity occurs where the 'Exchange Status is Rejected,' then a 'Notify Customer' activity must eventually occur after it within 0 to 1 hours. This sequence ensures the customer is informed of rejections promptly, with one notification satisfying multiple rejections.
3. If a 'Process Exchange' activity occurs, then a 'Record Transaction' activity must eventually occur after it within 0 to 1 hours where the 'Transaction ID' matches. This ordered progression guarantees that logging for accounting follows processing directly in terms of obligation.

#### **Succession Constraint**
The 'Receive Currency' activity and 'Reject Exchange' activity must not occur such that 'Receive Currency' is followed by 'Reject Exchange' at any later point, nor can 'Reject Exchange' be preceded by 'Receive Currency.' This contrast restricts the prohibited sequence, preserving the model's defined flow by preventing rejection after initial receipt.

### **Immediate Ordering Constraints**

#### **Chain Succession Constraints**
1. Whenever a 'Calculate Exchange Rate' activity occurs, it must be immediately followed by an 'Update Exchange Rates' activity with no other events in between within 0 to 30 minutes, and vice versa. This enforces a tightly coupled sequence with a direct cause-and-effect relationship, ensuring the computed rate is refreshed consecutively.
2. Whenever a 'Receive Currency' activity occurs, it must be immediately followed by a 'Record Transaction' activity with no other events in between within 0 to 1 day where the 'Transaction ID' matches, and vice versa. This cause-and-effect pairing guarantees that submission and logging form an uninterrupted, one-to-one immediate succession.
